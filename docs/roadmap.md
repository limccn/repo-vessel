## 二、五版设计留下的三条教训

### 1. 每砍一次，主张更清楚

| 版本 | 主张 | 那次砍掉了什么 |
|---|---|---|
| v1 | 社区灵龛 + 整理工具 | —— |
| v2 | 用 Dota 机制包装玩法（充能、榜单、Agent） | 部分社区设想 |
| v3 | 帮开发者**做决定**（Fork 溯源、余热提取） | 泛社区，收窄到个人整理 |
| v4 | 轻量、Topic 优先 | 余热、Agent、社区互动 |
| v4.1 | **娱乐优先、只读、可退出** | 充能积分、社区、私有仓库、组织仓库、Agent、年度报告 |

五次里每一次都更窄，而每一次都更能说清「打开它有什么好处」。**v4.1 是被最多次删除验证过的一版，
应当被当作路线图的基线，而不是又一次迭代的起点。**

### 2. 被砍两次以上的东西不要复活

私有仓库、组织仓库、GitHub 写操作、Agent / MCP、社区互动（评论 / 点赞 / 故事投稿）、
年度报告、回魂录、工时估算、代码内容扫描 —— 这些在 v1–v3 出现过，在 v4 与 v4.1 被连续砍掉两次。
它们不是「以后再说的好点子」，是**已经被否决过两次的方向**。任何一版路线图都不应该把它们重新列进去。

### 3. 被砍的东西只有「重新定义成只读」才回来

充能是唯一被重新打开的概念。它回来的方式值得记住：不是「发积分、买徽章、攀比等级」，
而是**从公开仓库数派生出的、不可购买、不可刷的等级**（`src/shared/tier.ts`）。

这条给出一个可以反复使用的判据：

> 一个被砍掉的概念，只有在能被改写成「只读、可解释、不激励用户做任何额外动作」的形式时，
> 才有资格回到路线图。

## 三、路线图的一条主线

```
GitHub 元数据读取 ──┬─→ 鉴定结果（匿名可用）──┬─→ 分享卡
                    │                          └─→ 仓库详情 / Fork 来路
                    └─→ 收集中枢（Topic 发现 + 核实）→ 三张榜单
                                                      └─→ 认领 / 隐藏 / 下架
```

三条由此推出的硬约束：

1. **匿名查询必须先于榜单。** 用户打开站点、输入用户名、看到真实数字 —— 这是产品的全部价值。
   榜单是「顺便看看别人」，不是入口。
2. **榜单与所有者控制必须同时上线。** 一旦站点开始公开列出别人的仓库，「隐藏」与「下架」就不再是
   下一个功能，而是这次上线的**前提**。v4.1 §12.3 明确要求不能只提供需要登录的退出路径。
3. **登录已经在了，但它现在没有可做的事。** 认领只有在仓库被收录之后才有意义 —— 所以登录不能
   单独撑起一个里程碑，它必须被花在 M3 上，而不是再等一个版本。

## 四、里程碑

### M1 · 真数据（已完成，2026-11-01）

**用户拿到什么：** 输入任意 GitHub 用户名，看到**真实**的公开仓库、真实沉睡天数、真实 Star 数；
数据不完整时看到「本次结果可能不完整」，而不是一个看起来正常的空列表。

| 交付 | 说明 |
|---|---|
| `GET /api/inspect/:username` | 个人账户校验（`type === "User"`）→ 分页读取公开仓库 → 按契约装配 `InspectPayload` |
| `GET /api/repos/:owner/:repo` | 单仓库元数据 + Fork 上游三态（personal / org / unresolved / unreachable） |
| GitHub 客户端 | `src/worker/github/` —— 全仓库唯一能碰 `api.github.com` 的地方；超时、限流识别、UA |
| 服务端凭据 | 见 §五.1，**没有它这个里程碑做不成** |
| D1 缓存 | `migrations/0001_repo_cache.sql` + 读写层；TTL 与 `readAt` 一起决定 `completeness` |
| SPA 接线 | `InspectRoute` / `ReposRoute` 把 `mockInspect()` 换成真实取数；`mock/` 保留给测试与演示 |

**验收**
- 用一个真实账号对照 github.com 核对仓库数、最后推送日期、Star 数；
- 断掉凭据或打满限流时，页面显示 `failed` / `partial` + 原因，**不显示 0 个仓库**；
- 被查询的组织账户返回 `personal-only`，页面说明「本站只收录个人公开仓库」；
- 缓存命中时 `readAt` 是抓取时间，不是请求时间。

**不做：** 不写 D1 的收录表、不做榜单、不做认领。M1 只让「看看自己」这条路变真。

**落地记录（2026-11-01）：** 两个接口、GitHub 客户端、派生层、D1 缓存与 SPA 接线全部上线，
172 个测试、设计审计与构建全绿。实际做法与计划的三处偏差已写回任务文档：SPA 取数层放在
`src/frontend/api/`（不是 `lib/api.ts`）；过期缓存**原样返回**而不改写成 `partial`（旧不等于
不完整，陈旧由 `readAt` 承担）；Fork 上游靠逐仓库补读 `parent`（列表接口不返回它），
按 `pushed asc` 取最沉睡的 25 个、8 路并发，失败保持 `unresolved`。

### M2 · 传播（已完成，2026-11-01）

**用户拿到什么：** 鉴定结果可以变成一张图，存下来发朋友圈 / 发推；别人点分享链接时能看到预览卡。

分两半，因为实现成本差得很远：

| 半 | 交付 | 成本 |
|---|---|---|
| M2a · 客户端图片卡 | `SharePanel` 用 `canvas` 画一张 PNG，下载 / 分享；复用 `tokens.css` 的颜色与 `lib/share.ts` 的文案 | 小，无新依赖 |
| M2b · 服务端 OG 图 | `GET /og/u/:username` 返回 PNG；`index.html` 的 `og:image` 按路由切换 | 中，需要 WASM 渲染器（Satori / resvg 一类） |

**为什么 M2a 先做：** 目前 `SharePanel` 只能复制文字。v4.1 §13.1 把「灵龛鉴定卡」叫作主要传播物料，
而一张能存的图是它唯一的形态。它不依赖服务端，能立刻上线。

**M2b 的前提：** OG 图必须是 PNG —— Twitter / 微信 / 微博都不支持 SVG 预览。这意味着一笔新依赖，
应当等 M1 稳定、数据可信之后再引入。

**不做：** 不做多套卡片风格（v4.1 §13.1 的「重新选择卡片风格」属于增强）；不做自动发布；
不做任何 `@` 提及。

**落地记录（2026-11-01）：** 两半都上线。客户端卡是浏览器 canvas，颜色从 `tokens.css` 的
自定义属性读出来，**没有一个 hex**；服务端 OG 图用 `@resvg/resvg-wasm` + 手写 SVG +
构建期字体子集，Worker 打包 2645 KiB / gzip 1043 KiB、启动 3 ms，都在预算内。同一份
`InspectPayload` 走 `loadInspectEnvelope`，两个出口的 `readAt` 是同一个时刻。

三处值得记住的取舍：

- **未知写成 `? 未知`，包括称号。** 读不到时（不存在 / 组织 / 限流）**照常画图**，没有一个
  字段被补成默认值；只有渲染本身失败才 302 到品牌图 —— 宁可给品牌图，不给破图。
- **字体是两份静态子集，不是一份可变字体。** resvg 不插值字重轴，只给一份可变字体时
  `font-weight="700"` 与 `400` 逐字节相同（实测）。钉死 `wght` 各切一份，合计 153 KB，
  反而比一份带轴的 130 KB 之外的方案更小。
- **OG 图不进 D1。** 40 KB 的可再生产物，`caches.default` 足够；多一张表就多一次迁移、
  备份和清理。缓存键去掉查询串并统一小写。

### M3 · 入龛（收录、榜单、所有者控制）—— 已完成，2026-11-01

**这是唯一一个「必须一起上线」的里程碑。** 拆开发布等于让站点先把别人的仓库挂上去、
再补上让人拿下来的按钮 —— 与 `CLAUDE.md` 的产品边界直接冲突。

| 交付 | 说明 |
|---|---|
| 收集中枢 | Cron Trigger：按配置的主题搜索 → 逐仓库核实（公开、个人账户、主题仍在、未被隐藏）→ 写 `collected_repo` |
| 核实状态 | `verify_state` 记录每次核实结果；无法再次确认时**隐藏**而不是假定仍公开 |
| `GET /api/collection-status` | 粘贴仓库链接查收录状态，五态文案见 v4.1 §11.2；不需要登录 |
| `GET /api/board/:board` | 三张榜单；只返回已核实且未隐藏的仓库；页头永远带「排名只来自本站已核实的仓库」 |
| `GET/POST/PATCH /api/claim/:owner/:repo` | 认领四项校验：当前用户是所有者、所有者是个人账户、仓库当前公开、仓库已被收录 |
| `POST /api/takedown` | **匿名可用**。这是登录之外的退出路径，不能要求 GitHub 登录 |
| 隐藏语义 | 隐藏优先于主题：即使主题还在，也不重新展示 |
| 下架传播 | 仓库下架时，本站可控的分享页与 OG 图缓存一起失效 |

**验收**
- 一个带主题的仓库在两次 cron 之间能被发现并进入榜单；
- 隐藏之后重新扫描，列表里仍然没有它；
- 匿名提交下架申请成功，并留下可查的状态；
- 仓库转为私有 / 转入组织 / 丢掉主题后，下一次核实把它下架。

**不做：** 不做投票、评论、榜单内互动；不做「最懒开发者」类排序；不做自动同步或建议。

**落地记录（2026-11-01）：** 九条接口与一次 Cron 全部上线，`0002_collection.sql` 四张表，
SPA 四页接线完成；`npm run typecheck` / `lint` / `test`（285 个）/ `build` /
`audit:design` / `audit:og-font` 六道门禁全绿，本地 `wrangler dev` 冒烟走通
（空榜 `complete`、工单可查、未知榜单 400、缺表时 `failed` 而不是空列表）。

四处值得记住的取舍：

- **核实失败要连续六次才下架，不是一次。** 单次失败多半是限流或超时，一次就翻转会把
  「网络抖了一下」写成「仓库没了」。`MAX_VERIFY_FAILURES = 6`（`src/worker/collect/budget.ts`），
  成功核实清零；限流则根本不记失败 —— 配额问题不是仓库的问题。
- **下架申请不自动隐藏。** 匿名提交分不清所有者与路人，立即生效等于给任何人一个
  「让任意仓库从榜单消失」的按钮。工单落库、承诺 24 小时，处理由维护者执行
  （`docs/runbook.md`）。
- **`GET /api/claims` 是后加的第五条。** 设计里写的是「管理页列出我的认领」，而没有
  这个接口就画不出来；读不到时返回 `failed`，绝不返回空列表 —— 那会让所有者以为认领丢了。
- **榜单只读 D1，一次上游请求都不打。** 榜单的 `readAt` 是 D1 读到的时刻，年龄由它承担；
  D1 挂了就是 `failed`，不是「今天没有沉睡的仓库」。

### M4 · 测量 —— 已完成，2026-11-01

v4.1 的 MVP 到这里就交付完了。**之后的第一件事不是加功能，是测量** —— 也就是 v4.1 §17 的七项指标：
查询发起率、查询成功率、分享卡生成率、分享链接访问量、主题复制次数、认领与隐藏成功率、误收录与下架处理时间。

在拿到这些数字之前，任何新功能都只是在猜。

**落地记录（2026-11-01）：** 七项指标的采集、存储与只读报告全部上线。
`0003_metrics.sql` 建了 `metrics_daily`（日 × 事件 × 维度一行，主键即聚合键）；
`src/shared/metrics.ts` 是 SPA 与 Worker 共用的事件词汇；客户端三类事件走
`POST /api/metrics/event`（`sendBeacon` 优先，DNT / GPC 时一条不发），服务端五类事件在
鉴定、认领、工单、分享页与 Cron 里旁路写入；`npm run metrics` 用两条只读 SQL 生成 Markdown，
缺表时退出码 0、整页写「未采集（迁移未应用）」。`docs/metrics.md` 是口径的唯一出处，
`docs/runbook.md` 第五节是命令。

四处值得记住的取舍：

- **指标是旁路。** 端点写库失败仍回 `204`；没有 D1 时主流程照常。任何采集失败都不改变
  一条响应 —— 否则「统计」会变成新的故障源。
- **三态，不是两态。** 未采集 / 0 / 有值分得比「0 和 nonzero」细一档。缺表、DNT、拦截器
  都会让计数缺席，把它们写成 0 是最容易被相信的错误。
- **不建事件流表、不加 `ip_hash`。** 一行只到「某天某类事件发生了几次」；
  能聚合出趋势，不能还原成一个人。
- **复制主题按配置里的每个 slug 各给一个按钮。** 交互稿写的是「复制第一个主题」，实现时
  改成逐个复制：GitHub 的 Settings → Topics 一次只收一个主题，而配置允许任意多个；
  `topic_copy` 的维度本来就是 `topic=<slug>`，逐个记反而能看出哪一个真被用上。

报告**不写进 CI，也不自动提交**：它需要远端 D1 与登录态。首份生产报告要等上线后的真实
流量；在此之前，报告正确地显示「未采集」。

候选方向（**都还没有被决定**，等数据说话）：
- 分支领先 / 落后比较（v4 明确延后的一项）
- 更多卡片风格与分享模板
- i18n（`src/shared/copy.ts` 的 `Locale` 已经预留了四个语种，切换器是独立任务）
- 仓库详情抽屉的深度（目前规划里的 M4 抽屉）

## 五、M1 开场前必须定的三件事

### 1. 服务端 GitHub 凭据 —— 不定就没有 M1

未认证的 GitHub API 是 **每个 IP 每小时 60 次**。Cloudflare Workers 的出向 IP 不稳定且与他人共享，
所以「匿名查询」在共享 IP 上会把 60 次配额分给所有访客 —— 实测意义上等于零。

结论：**数据读取必须用一个服务端凭据**（细粒度 PAT，只读 public，或一个 GitHub App）。
它和用户登录是两回事：

| | 用途 | 生命周期 | 存在哪 |
|---|---|---|---|
| 用户 OAuth token | 只用来确认「你是谁」（`GET /user`） | 读完即弃 | 不落任何存储 |
| 服务端凭据 | 读公开仓库元数据 | 长期 | Wrangler secret |

把两者混用会同时坏掉两件事：用户的配额被站点消耗，站点的数据又随某一次登录过期而失效。

### 2. 缓存与 TTL

D1 缓存是命中率与新鲜度的交易。需要先定下：缓存键（`full_name`）、TTL（元数据可以天级）、
以及**过期数据怎么呈现** —— 按交互规范，过期不是删除，是 `completeness: "partial"` + 明确的 `readAt`。

### 3. 分页上限与「不完整」的语义

一个有一千个仓库的账户要不要全读？路线图的建议是：设一个页数上限，超过就返回 `partial` 并列出
`missingPages`，界面如实说明。**宁可说「没读完」，也不要悄悄截断。** 这条在 M1 就要定，
否则后面每个接口都要返工。
