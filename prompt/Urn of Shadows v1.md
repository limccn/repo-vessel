# 影之灵龛：GitHub 仓库的数字归宿

> **不是每个仓库都需要继续活跃，但每个曾经开始的项目，都值得被妥善安放。**

## 一、项目定位

### 1. 产品是什么

**影之灵龛**，英文暂名 **Urn of Shadows**，是一个面向 GitHub 用户的单页面网站。

它帮助用户发现长期不活跃的仓库，理解这些仓库的现状，并为它们选择下一步：继续维护、暂时收藏、归档，或在用户明确同意后展示给社区。

它兼具三种属性：

- **工具性**：扫描、筛选和诊断仓库，提供可执行的整理建议。
- **娱乐性**：将沉睡仓库包装为「入龛」「余烬」「唤醒」等轻量游戏化体验。
- **社交性**：通过榜单、分享卡片和徽章，让仓库的故事被看见。

### 2. 产品要解决的问题

GitHub 用户会随着学习、工作和兴趣变化，积累大量仓库：

- 当初为了学习而创建，提交几次后就搁置；
- 因为好奇 fork，之后再也没有跟进上游；
- 项目暂时结束，但不舍得删除；
- 仓库列表越来越长，很难区分“值得继续”“暂时搁置”和“可以归档”；
- 一些旧仓库虽然不再更新，仍然有收藏、参考或再利用价值。

**核心矛盾不是“如何删除仓库”，而是“如何低压力地决定它们的去处”。**

### 3. 产品边界

这个产品不把不活跃等同于失败，也不替用户判断仓库是否“有价值”。

它提供的是：

> **发现 → 理解 → 决定 → 安放 → 分享**

而不是：

> 自动清理 → 批量删除。

**特别说明：**“入龛”是本产品内的标记，不会自动修改 GitHub 仓库；GitHub 的“归档”也不等于删除仓库，通常仍可查看和搜索。产品不能承诺将仓库从 GitHub 的所有列表或用户资料中隐藏。

## 二、目标用户与核心使用场景

### 目标用户

| 用户类型 | 典型需求 |
|---|---|
| 独立开发者 | 整理个人账号中多年积累的实验项目 |
| 学习型开发者 | 找回曾经 fork 但没有继续学习的项目 |
| 开源维护者 | 判断哪些项目需要继续维护，哪些适合归档 |
| GitHub 重度用户 | 管理大量仓库，同时保留自己的技术足迹 |
| 社区参与者 | 分享有趣的旧项目，发现仍有参考价值的仓库 |

### 核心场景

1. **“我的 GitHub 太乱了。”**  
   用户登录后扫描自己的仓库，筛选长期没有推送的项目。

2. **“这个 fork 还有必要留着吗？”**  
   用户查看上游是否仍活跃、自己是否做过改动，再决定保留、同步或归档。

3. **“我不想删，但也不想一直看到它。”**  
   用户将仓库标记为“已安放”，在本站的待处理列表中收起。

4. **“这个老项目还挺有意思。”**  
   用户自愿公开仓库，生成分享卡片或参与榜单。

## 三、产品概念与术语

建议借鉴“影之灵龛”的意象，但使用原创视觉和文案，不直接使用游戏中的装备图标、角色形象或具体技能数值。

| 产品术语 | 含义 |
|---|---|
| **灵龛** | 用户在本站用于安放仓库的个人空间 |
| **入龛** | 将仓库标记为“暂时安放”，仅影响本站状态 |
| **沉睡** | 一段时间内没有检测到新的仓库推送 |
| **余烬** | 仓库可能仍有参考或复用价值的信号，例如 Star、Fork |
| **唤醒** | 用户决定重新关注或维护仓库 |
| **安放** | 用户确认处理方式，例如保留、稍后处理或 GitHub 归档 |
| **灵龛档案** | 仓库的诊断摘要和处理记录 |
| **社区灵龛** | 用户主动公开参与展示的仓库集合 |

文案应带一点幽默，但避免“废物代码”“失败项目”等羞辱性表达。

## 四、单页面网站的信息架构

网站采用**单页面结构**：主要内容在同一页面，通过锚点导航、局部状态切换、抽屉或弹窗完成交互，不需要用户频繁跳转。

### 页面整体结构

```text
顶部导航
├── 产品 Logo 与名称
├── 灵龛榜单
├── 仓库诊断
├── 清理助手
├── 关于 / 隐私说明
└── GitHub 登录

首屏：一句话介绍 + 立即探索
├── 查看社区榜单
└── 登录并扫描仓库

社区灵龛与榜单
├── 榜单切换
├── 筛选与排序
└── 仓库卡片 / 榜单详情

我的灵龛
├── 登录引导与权限说明
├── 仓库扫描概览
├── 筛选与搜索
└── 我的仓库列表

仓库诊断
├── 仓库状态
├── Fork 溯源
├── 价值信号
└── 可选处理建议

清理助手
├── 建议操作
├── 命令预览与复制
└── Agent Skill 使用说明

分享与个人设置
├── 分享卡片和徽章
├── 公开参与管理
├── 数据与授权管理
└── 退出登录
```

### 导航与权限体验

- **未登录**：可浏览首屏、公开榜单、产品说明和公开仓库档案。
- **登录后**：可扫描可访问的仓库，查看个人诊断结果。
- **查看仓库详情**：在页面内打开右侧抽屉；移动端改为底部弹层或全屏面板。
- **执行处理**：先展示建议和影响，再由用户决定是否前往 GitHub 或复制命令。
- **分享**：由用户主动选择仓库、确认公开内容后生成。

## 五、页面内容与功能设计

## 1. 首屏：让用户立刻理解产品

### 推荐文案

**主标题：**

> 给那些不再更新的仓库，一个安放之处。

**副标题：**

> 扫描你的 GitHub，找回沉睡的项目。  
> 保留记忆，整理仓库，让旧代码继续发光。

**主要按钮：**

- `连接 GitHub，看看我的灵龛`
- `先逛逛社区榜单`

**辅助说明：**

> 默认只读取信息，不会删除或修改你的仓库。

### 首屏视觉

- 一个原创的抽象灵龛或容器作为主视觉；
- 周围漂浮代表仓库的代码碎片、星星和微弱光点；
- 整体气质偏安静、神秘、温暖，而不是恐怖墓地；
- 可展示示例统计卡片，但必须明确标注“示例数据”。

## 2. 社区灵龛：榜单与发现

### 参与原则

榜单只展示**明确同意公开参与**的公开仓库。私有仓库不进入公开榜单。

用户参与方式：

1. 在本站登录后，选择自己的公开仓库并确认参与；
2. 或手动给公开仓库添加指定 Topic，例如 `urn-of-shadows`，作为**自愿参与的信号**。

建议将两种方式理解为：

- **本站确认**：立即进入本站的公开候选池；
- **添加 Topic**：允许产品发现该仓库，但不保证 GitHub 搜索结果能实时或完整覆盖所有仓库。

产品应提供退出方式：撤回本站公开同意；如果通过 Topic 参与，也需提示用户移除 Topic。退出后榜单和本站生成的公开档案应在明确时限内下架。

### 榜单玩法

#### 榜单 A：最长沉睡榜

展示长时间没有检测到推送的公开仓库。

- 排序：按最后推送时间从早到晚；
- 标签示例：`已沉睡 1,248 天`；
- 说明：反映的是仓库推送情况，不代表作者本人长期没有活动。

**推荐文案：**

> 它们没有消失，只是在时间里安静地待着。

#### 榜单 B：余烬未熄榜

展示长期沉睡，但仍获得关注的仓库。

- 条件：超过设定时间未推送；
- 排序：按 Star 数或 Fork 数；
- 用途：发现“项目不再活跃，但可能仍有参考价值”的仓库。

**推荐文案：**

> 即使不再更新，也曾照亮过别人。

#### 榜单 C：沉睡仍被传承榜

展示长期沉睡，但最近仍被 Fork 的仓库。

- 排序：按可获取到的最近 Fork 创建时间；
- 展示：`最近一次可见 Fork：2026-05-12`；
- 如果数据不可获得，显示“暂无可用数据”，不参与该项排序。

**推荐文案：**

> 故事停在这里，灵感却在别处继续。

#### 榜单 D：Fork 时光胶囊

展示上游已有变化，而用户的 Fork 长期没有更新的仓库。

- 需要在能可靠比较双方分支时才展示差异；
- 不将“落后上游”直接等同于“需要同步”，因为 Fork 可能本来就用于独立开发。

**推荐文案：**

> 你停下的地方，上游可能还在前进。

#### 可选后续玩法：唤醒榜

展示用户主动标记为“重新开始维护”的仓库。

- 唤醒是用户主动选择，不自动推断；
- 可分享“沉睡多久后重新开始”的故事；
- 不要求用户持续提交，避免制造打卡压力。

### 通用筛选与排序

所有榜单尽量提供统一的筛选和排序控件：

**筛选：**

- 语言；
- 原创仓库 / Fork；
- 沉睡时间：例如 6 个月、1 年、3 年以上；
- Star 数区间；
- Fork 数区间；
- GitHub 是否已归档。

**排序：**

- 最后推送时间；
- 默认分支最后提交时间；
- Star 数；
- Fork 数；
- 最近可见 Fork 创建时间。

由于不同榜单的主题不同，可以设置一个默认排序，但允许用户切换。缺失数据应明确标为“未知”，不能与零混为一谈。

### 榜单卡片内容

每张卡片建议包含：

- 排名；
- 仓库名称和所有者；
- 仓库简介；
- 主要语言；
- Star 和 Fork 数；
- 最后推送时间与沉睡时长；
- 已归档、Fork 等状态标签；
- `查看档案`、`访问 GitHub`、`分享`。

**示例：**

> **#12 · alex/old-side-project**  
> 曾经想做一个更简单的记账工具。  
> TypeScript · ⭐ 128 · Fork 23  
> 最后推送：1,248 天前  
> `沉睡中` `余烬未熄`

## 3. 我的灵龛：扫描与整理

### 登录前

展示明确的权限说明：

> 登录后，我们可以帮助你发现和整理仓库。  
> 扫描默认只读取仓库信息，不会替你归档、删除或修改仓库。

按钮：

- `使用 GitHub 登录`
- `了解数据和权限`

### 登录后概览

展示四张概览卡片：

1. **已扫描仓库**
2. **长期沉睡仓库**
3. **等待决定的 Fork**
4. **已在本站安放**

点击卡片后，仓库列表自动应用对应筛选条件。

### 扫描范围

默认先扫描用户自己的仓库，提供清晰的范围提示：

- 公开仓库；
- 如后续支持私有仓库，必须单独明确授权；
- 组织仓库和作为协作者可访问的仓库，不应默认混入“我的个人仓库”；
- 提供扫描进度、取消按钮和结果更新时间。

### 仓库列表

每条仓库展示：

- 名称、简介、语言；
- 原创 / Fork；
- 公开 / 私有；
- 最后推送时间；
- Star / Fork 数；
- 是否已经 GitHub 归档；
- 本站处理状态：`待处理`、`已安放`、`计划唤醒`；
- `查看诊断`、`标记安放` 等按钮。

### 搜索与筛选

- 按仓库名称搜索；
- 按最后推送时间排序；
- 按原创 / Fork 筛选；
- 按是否已归档筛选；
- 按本站处理状态筛选；
- 排除用户不想处理的仓库；
- 支持多选，生成批量处理清单。

**注意：**批量选择只用于整理清单和生成建议，不意味着产品自动批量修改 GitHub。

### 本站状态设计

| 状态 | 含义 | 是否修改 GitHub |
|---|---|---|
| 待处理 | 还没有决定如何处理 | 否 |
| 已安放 | 暂时从本站待处理列表中收起 | 否 |
| 计划唤醒 | 用户打算重新关注 | 否 |
| 忽略 | 用户不希望继续收到整理提示 | 否 |
| GitHub 已归档 | 从 GitHub 读取到的实际状态 | 此状态由 GitHub 决定 |

## 4. 仓库诊断：帮助用户做决定

点击仓库后打开诊断抽屉。

### 诊断信息结构

#### A. 仓库基本状态

- 仓库名称、描述、所有者；
- 创建时间；
- 最后推送时间；
- 如可获取，默认分支最后提交时间；
- 是否为 Fork；
- 是否已归档；
- Star、Fork、开放 Issue 等公开或授权可见信息。

#### B. 沉睡状态

按最后推送时间给出易理解的提示：

- `近期活跃`：过去 6 个月有推送；
- `逐渐安静`：6–12 个月没有推送；
- `长期沉睡`：1 年以上没有推送；
- `状态未知`：数据不足或仓库为空。

这些阈值是产品默认值，后续可允许用户调整。

#### C. Fork 溯源

对于 Fork 仓库，展示：

- Fork 来源及 GitHub 提供的上游信息；
- 上游仓库是否仍可访问；
- 上游是否已归档；
- 上游最后推送时间；
- 在有权限且分支可比较时，展示 Fork 相对上游的差异；
- 如果无法访问或比较，显示具体原因，例如“上游不可访问，无法判断”。

可以提供面向用户的问题：

> 你当初 Fork 它，是为了学习、收藏，还是已经做过自己的修改？

### 建议规则示例

| 发现 | 展示建议 | 注意事项 |
|---|---|---|
| 长期无推送，但有 Star 或 Fork | 保留或归档，并检查 README 是否说明项目状态 | 关注数不直接代表实际价值 |
| Fork 长期未更新，上游仍活跃 | 查看上游变化，决定是否同步 | 同步可能影响当前分支，不能自动执行 |
| Fork 有自己的独立修改 | 先检查差异，再决定是否继续维护 | 不能仅因上游活跃就建议覆盖 |
| 上游已归档 | 将其作为历史快照保留，检查是否仍有依赖 | 上游归档不代表代码不可用 |
| 上游不可访问 | 提示无法确认状态 | 不推断为“上游已删除” |
| 当前仓库已经归档 | 提示已归档，可保留现状 | 不重复建议归档 |
| 信息不足 | 提示用户手动查看 | 不生成确定性结论 |

### 处理选项

- `暂时保留`：记录在本站；
- `入龛安放`：从本站待处理列表中收起；
- `计划唤醒`：标记后续关注；
- `前往 GitHub 查看`；
- `查看归档说明与命令`；
- `查看 Fork 同步说明`。

每个建议旁边都应说明：**为什么提出这个建议、依据是什么、哪里可能判断不准。**

## 5. 清理助手与 Agent Skill

### 产品目标

将诊断结果转化为用户或 Agent 可理解的整理清单，但不让 Agent 在未经确认的情况下修改仓库。

### 网站端体验

用户选择一个或多个仓库后，生成一份清单：

- 仓库名称；
- 诊断摘要；
- 建议动作；
- 建议原因；
- 潜在影响；
- 是否需要 GitHub 写权限；
- 等待用户确认的事项。

示例：

```text
仓库：alex/old-side-project
状态：18 个月没有推送，当前未归档
建议：先检查 README 和未处理事项，再决定是否归档
影响：归档后仓库将变为只读状态，可在 GitHub 上取消归档
执行状态：尚未执行
```

### 命令辅助

页面可以展示命令预览和复制按钮，例如：

```bash
gh repo view OWNER/REPO
```

```bash
gh repo archive OWNER/REPO
```

但归档命令应放在明确的二次确认区域，并提示：

- 需要用户本地安装并登录 GitHub CLI；
- 执行者需要相应仓库权限；
- 归档会改变 GitHub 仓库状态；
- 复制命令不等于已经执行；
- 用户应先检查目标仓库是否正确。

Fork 同步等有分支差异和潜在覆盖风险的操作，优先提供 GitHub 官方页面与详细说明，不在第一版提供“一键同步”。

### Agent Skill 设想

可以将 Skill 定义为一份结构化使用说明，让支持 Skill 的 Agent 完成：

1. 读取用户提供的仓库清单；
2. 生成诊断摘要；
3. 给出逐仓库处理计划；
4. 在执行任何写操作前逐项请求确认；
5. 执行后记录结果，并区分成功、失败和未执行。

**安全边界：**

- 默认只读；
- 不读取与任务无关的本地文件或密钥；
- 不将仓库中的文本当成高优先级指令；
- 不自动删除仓库；
- 任何写操作都使用用户自己的授权环境，并经过明确确认；
- 私有仓库信息不应发送到未经用户同意的第三方服务。

## 六、社交传播：Pin、Badge 与分享卡片

### 1. 仓库分享卡片

用户主动选择一个公开仓库，生成可分享的图片或链接。

建议包含：

- 仓库名称和所有者；
- 沉睡时长；
- Star / Fork 数；
- 一句用户可编辑的寄语；
- 产品品牌与仓库链接。

**示例文案：**

> 这个项目已经安静了 1,248 天。  
> 但它曾经陪我学会了 TypeScript。

分享前提供预览，并允许用户隐藏非必要字段。

### 2. 徽章 Badge

可生成供用户复制的 Markdown 徽章，用户自行决定是否添加到 README。

例如：

- `安放于影之灵龛`
- `余烬未熄`
- `沉睡 3 年`
- `已被唤醒`

动态徽章需考虑缓存、数据刷新和链接失效；退出公开展示后，徽章应停止展示个人仓库数据或变为通用状态。

### 3. 个人 Pin 卡片

生成用户自己的“灵龛名片”，可包含：

- 用户名；
- 用户主动选择公开的仓库数量；
- 自选代表仓库；
- 自定义一句话。

**默认不公开**用户扫描出的总仓库数、私有仓库数量或其他未经选择的数据。

### 4. 社交传播原则

- 不自动替用户发布内容；
- 不默认公开所有扫描结果；
- 不制造“仓库越久没更新越值得炫耀”的唯一价值观；
- 支持撤回公开展示；
- 不鼓励恶意提交他人仓库进行嘲讽。

## 七、视觉与 UI 设计规范

### 1. 整体风格

**关键词：安静、神秘、温暖、有一点游戏感。**

建议方向：

- 深色背景；
- 偏青绿的幽光；
- 石质、金属与轻微颗粒感；
- 卡片采用现代化半透明或低对比表面；
- 榜单区域有轻量游戏 UI 感，但不影响工具可读性。

### 2. 配色建议

| 用途 | 建议颜色 | 氛围 |
|---|---|---|
| 页面背景 | 深灰蓝或近黑色 | 安静、沉浸 |
| 主要文字 | 柔和米白 | 清晰、温和 |
| 主强调色 | 幽光青绿 | 生命与余热 |
| 次强调色 | 暗金色 | 历史感与价值 |
| 警示色 | 柔和琥珀色 | 提醒而非恐吓 |
| 危险操作色 | 暗红色 | 明确区分高风险操作 |

确保文字、按钮和状态标签具有足够对比度，不能只靠颜色区分状态。

### 3. 字体与排版

- 中文使用清晰的现代无衬线字体；
- 仓库名、命令和数据使用等宽字体；
- 标题有适度仪式感，正文保持工具类产品的易读性；
- 留白充足，卡片信息分层清晰。

### 4. 响应式设计

- **桌面端**：榜单多列卡片，仓库诊断使用右侧抽屉；
- **平板端**：减少列数，筛选项可折叠；
- **移动端**：单列卡片，诊断使用底部弹层或全屏面板；
- 列表支持键盘访问，动画支持减少动态效果设置。

### 5. 关键状态

设计稿需要覆盖：

- 未登录；
- 正在授权；
- 扫描中；
- 扫描完成；
- 没有符合条件的仓库；
- API 限流；
- 权限不足；
- 上游不可访问；
- 公开分享确认；
- 网络错误与重试。

## 八、核心用户流程

### 流程一：扫描并安放仓库

```text
进入首页
→ 使用 GitHub 登录
→ 查看权限和扫描范围
→ 开始扫描
→ 查看沉睡仓库列表
→ 打开某个仓库诊断
→ 选择“入龛安放”
→ 仓库从本站待处理列表中收起
```

### 流程二：将仓库公开加入社区

```text
选择自己的公开仓库
→ 预览将公开的信息
→ 同意参与社区展示
→ 加入候选池
→ 满足榜单条件后展示
→ 生成分享卡片或 Badge
```

### 流程三：通过 Topic 参与

```text
用户在 GitHub 手动添加指定 Topic
→ 网站按计划发现或用户主动提交仓库链接
→ 验证仓库为公开状态及 Topic 存在
→ 加入公开候选池
→ 用户可移除 Topic 并申请下架
```

### 流程四：使用清理助手

```text
选择待处理仓库
→ 生成诊断与处理清单
→ 查看每项建议的依据和影响
→ 复制命令，或交给 Agent 生成执行计划
→ 用户逐项确认
→ 在用户自己的 GitHub 授权环境中执行
→ 查看执行结果
```

## 九、数据口径与授权边界

<details>
<summary><strong>供产品经理与开发确认：数据定义和技术约束</strong></summary>

### 1. “沉睡”如何计算

建议第一版统一使用仓库的**最后推送时间**作为“沉睡天数”的基础：

- 最后推送不等于最后提交；
- 推送也不一定由仓库所有者本人完成；
- 默认分支最后提交时间可以单独展示；
- 无法取得时间或仓库为空时，显示“未知”，不强行上榜。

因此，“最长遗弃榜”建议改名为**最长沉睡榜**，避免误解为作者个人不活跃。

### 2. “最近被 Fork 时间”

可在 GitHub API 返回的数据范围内，按 Fork 创建时间获取最近可见 Fork。

需要说明：

- 请求可能受到权限、分页和限流影响；
- 无法取得数据不代表从未被 Fork；
- 榜单应记录数据更新时间；
- 第一版不承诺对所有 GitHub 仓库进行实时、完整的全网统计。

### 3. 授权建议

- 公开社区内容可在未登录状态下浏览；
- 公开仓库数据不必一开始就要求仓库写权限；
- 如果支持扫描私有仓库，应单独说明访问范围和读取内容；
- “只读扫描”与“实际归档、同步等写操作”应明确分离；
- 添加或移除 GitHub Topic 属于修改仓库信息，不能在只读授权下由网站自动完成；
- 实际权限粒度、OAuth 或 GitHub App 的选型，需要在开发前按所使用的 GitHub API 和目标场景核对。

### 4. 数据与隐私

建议公开说明：

- 读取哪些数据；
- 保存哪些数据，以及保存多久；
- 私有仓库是否被服务端存储；
- 分享和榜单数据的刷新频率；
- 用户如何退出展示、撤销授权和删除本站数据。

公开仓库也不应默认进入榜单；“公开可访问”不等于“同意被产品展示”。

</details>

## 十、版本规划

### MVP：先验证整理需求

建议第一版只做：

1. 产品首页与权限说明；
2. GitHub 登录；
3. 扫描用户自己的公开仓库；
4. 按最后推送时间筛选和排序；
5. 基础仓库诊断与 Fork 上游状态展示；
6. 本站“入龛 / 保留 / 忽略”标记；
7. 用户主动选择公开仓库参与榜单；
8. 一张分享卡片；
9. 隐私说明、退出展示和数据删除入口。

**第一版不做：**

- 自动修改 GitHub 仓库；
- 私有仓库公开展示；
- 批量删除；
- 自动同步 Fork；
- 复杂积分和排行榜竞技；
- 承诺全网实时扫描所有带 Topic 的仓库。

### 后续迭代

- 私有仓库的独立授权与诊断；
- 更深入的 Fork 差异分析；
- Agent Skill 和批量计划导出；
- 动态 Badge；
- 唤醒故事和用户寄语；
- 可配置的沉睡阈值；
- 更丰富的榜单与社区发现。

## 十一、与产品经理重点讨论的问题

1. **核心价值优先级**：先做个人整理工具，还是先做社区榜单传播？
2. **公开参与方式**：Topic 是否直接视为公开同意，还是仅作为发现信号，仍需所有者在站内确认？
3. **隐私边界**：第一版是否只支持公开仓库，暂不接触私有仓库？
4. **扫描深度**：第一版是只读仓库元数据，还是需要读取部分文件和提交信息？
5. **沉睡定义**：默认采用 6 个月还是 12 个月作为主要筛选阈值？
6. **本站“入龛”的意义**：仅在本产品中整理，还是未来提供更丰富的收藏与回顾？
7. **社交调性**：突出幽默趣味，还是突出开发者的项目记忆与温暖叙事？
8. **成功指标**：以完成扫描和整理为主，还是以公开分享和邀请传播为主？

**建议的产品主线：**

> 以“帮用户整理仓库”为核心价值，以“让旧代码的故事被看见”为传播亮点。
