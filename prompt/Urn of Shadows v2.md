
# 影之灵龛 Urn of Shadows · 产品定义草案 v0.1

## 1. 背景与问题定义

**场景**：GitHub 用户长期 fork / 创建仓库，提交过一两次后逐渐荒废。数年积累后，账号里堆满「准死亡」仓库：不想看、不想维护、又舍不得删。

**痛点拆解**：

| # | 痛点 | 表现 | 现有方案的不足 |
|---|---|---|---|
| 1 | 列表噪音 | Repository 列表被僵尸仓库淹没，找不到真正重要的项目 | GitHub 仅提供 Archive / 排序，无诊断 |
| 2 | 断舍离焦虑 | 删除有沉没成本与情感成本，「万一以后要用」 | 现有 cleanup 工具只做「删除」，制造焦虑而非缓解 |
| 3 | Fork 溯源困难 | 不知道上游是否已修复 / 已合并 / 已归档 / 被删 | GitHub UI 中 fork 与 upstream 关系弱，落后多少 commit 看不到 |
| 4 | 价值浪费 | 旧仓库里的文档、脚本、踩坑记录仍可复用 | 没有任何产品做「余热提取」 |
| 5 | 无社交出口 | 清理是一件孤独、无成就感的事 | 缺少晒单、比较、围观的传播场景 |

**核心主张**：不是「帮你删仓库」，而是**帮你在删之前，把剩余价值榨干净，并把这件事变成一件有仪式感、可炫耀、可分享的事**。

**产品类型**：Web 单页工具站（兼娱乐/社区榜单） + GitHub App（数据采集） + Agent Skill / MCP（清理能力输出）。

**目标用户**：
- 主：注册 3 年以上、仓库数 > 30 的开发者、fork 党、开源爱好者、独立开发者（22–38 岁）
- 次：技术博主 / Up 主（需要内容素材）、招聘者（看项目活跃度）、开源维护者（识别可回收的孤儿 fork）

## 2. 核心隐喻：把 Dota 装备机制翻译成产品机制

这是整个产品的灵魂，也是传播的记忆点。建议 PM 与设计都以这张映射表为准：

| Dota 元素 | 产品映射 | 说明 |
|---|---|---|
| 影之灵龛（骨灰盒） | 「我的灵龛」：被标记为休眠的仓库集合 | 用户把僵尸仓库「送进灵龛」，而不是删除 |
| 合成配方（面罩+圆环+指环+图纸，825 金） | **处置成本可视化**：归档一个仓库需要几步决策 | 用「合成」隐喻做处置向导 |
| 充能（敌方英雄 1500 范围内阵亡 +2） | **充能机制**：仓库每沉睡 N 天、或每次你做出一次处置决策，灵龛 +1 充能 | 冷启动：首次加入灵龛的仓库直接送 2 点充能（呼应「首次阵亡获得 2 点」） |
| 灵魂释放 · 友方回血（30/s，8s） | **余热提取**：从旧仓库导出文档 / 脚本 / 片段，复用到新项目 | 正向价值回收 |
| 灵魂释放 · 敌方伤害（25/s，8s） | **回流上游**：给上游提 PR / issue / 冲掉 fork 落后的 commit | 把「我落后了」转成行动 |
| 魂之灵瓮（进阶） | **处置进阶**：休眠 → 归档 / 复活 / 捐赠 / 转生（迁移合并到新仓库） | 高级形态 = 更彻底的处置 |
| 8 秒持续效果 | **8 天处置窗口**：诊断报告生成后 8 天内完成处置，否则充能衰减 | 制造轻量紧迫感（可关闭） |

> 文案基调：克制、玩梗、不羞辱用户。所有「遗弃 / 骨灰盒」措辞只在娱乐化榜单出现，工具流程内保持中性专业（「休眠 / 处置 / 归档」）。

## 3. 功能模块

### 3.1 采集与接入（数据来源）

- **Topic 标记法（主路径）**：用户给目标仓库打上 topic `urn-of-shadows`，系统通过 GitHub App webhook + 每日增量扫描拉取。
  - 优点：零成本筛选、用户自主圈定范围、天然形成公开社区（topic 页本身就是入口与传播位）。
- **辅助入口**：
  - 授权后扫描账号全部仓库（含私有，可选）
  - 手动粘贴 repo URL / 批量导入用户名
  - 组织（org）维度扫描，做公司级「仓库资产盘点」
- **权限（只读，最小化）**：
  - 未登录：只看公开榜单（public repo 数据）
  - 登录：`read:user` + `public_repo`；勾选「包含私有仓库」时才申请 `repo`（只读元数据，不读代码内容）
  - 明确声明：**不 clone、不存代码、不写入仓库**；所有写操作只在 Agent Skill 中且需用户显式确认

### 3.2 榜单系统（娱乐性 + 社交核心）

#### A. 排序/筛选维度（所有榜单通用）
Star 数、Fork 数、**最后提交时间**、**最后被 fork 时间**、仓库年龄、代码行数、语言、License、是否归档、是否私有、贡献者数、是否有 README/CI/测试。

时间切片：7 / 30 / 90 / 365 天 + 自定义区间。

#### B. 榜单玩法（建议至少做 6 个）

| 榜单 | 定义 | 主排序 | 传播玩法 |
|---|---|---|---|
| **最长遗弃榜** | 最后一次 commit 距今天数 | 沉睡天数 | 「你的仓库睡了 1024 天」年度梗图 |
| **明珠蒙尘榜** | Star 高（>100）但 1 年无更新 | Star × 沉睡天数 | 「这仓库当年要是继续做…」讨论贴 |
| **沉没成本榜** | commit 数 × 年龄 × 代码行数 | 投入工时估算 | 「我在这仓库上浪费了 200 小时」晒图 |
| **断根之木榜** | Fork 仓库，但上游已活跃更新 / 已修复 | 落后上游 commit 数 | 「上游都发 v3 了你还停在 v0.1」 |
| **上游已死榜** | 上游 archived / deleted / 改名失联 | 沉睡天数 | 「我是这个项目的唯一守墓人」徽章 |
| **孤本孤证榜** | 贡献者 = 1、fork = 0、star = 0 但代码量大 | 代码行数 | 「宇宙里只有我看过这段代码」孤独感徽章  | 
| **回魂复活榜**（周更） | 本周从休眠中复活（重新提交）的仓库 | 复活速度 / 沉睡天数 | 「睡了 892 天后它活了」故事征集 |
| **灵龛富豪榜** | 用户灵龛总充能数 / 处置仓库数 | 充能总数 | 用户主页排行，年度「骨灰盒奖」 |
| **判官/义工榜** | 给别人诊断报告投票、写处置心得的人 | 互动数 | 社区荣誉，换取徽章 |

#### C. 榜单互动机制（社交属性）
- **围观机制**：每个榜单条目支持「+1 共鸣」「😂」「🕯️ 上香」三种轻量表情，降低评论门槛
- **召唤机制**：生成「@repo-owner 的仓库已沉睡 XXX 天」分享卡片，可一键贴到 X / 小红书 / V2EX / 即刻
- **打卡机制**：每周一推送「本周处置挑战：清理 3 个仓库，充能 +6」
- **匿名开关**：榜单可选择实名 / 匿名 / 完全隐藏（用户对自己出现在榜单有完全控制权，默认公开但可退出——**这条必须做成一级设置**）
- **徽章体系**：
  - 「守墓人」处置 ≥10 个仓库
  - 「回魂师」复活 ≥3 个仓库
  - 「判官」参与诊断投票 ≥50 次
  - 「孤本收藏家」孤本榜上榜
  - 「骨灰盒满」灵龛充能 ≥825（呼应总价梗）
- **年度报告**：12 月推出「你的 GitHub 年度断舍离报告」，含沉睡天数、最大单仓投入、最可惜仓库、最成功复活——**这是主要传播抓手**，对标 GitHub Unwrapped / Spotify Wrapped。

### 3.3 仓库诊断（工具性核心）

目标：对单个仓库生成**结构化诊断报告**，回答「这仓库还活着吗？还值不值得留？」

#### A. 诊断维度

| 维度 | 检查项 | 输出 |
|---|---|---|
| **活性** | 最后 commit、最后 issue/PR、最后 release、最近 fork | 「休眠指数」0–100 |
| **投入度** | commit 数、贡献者数、代码行数、生命周期、语言分布 | 「沉没成本」估算（人时） |
| **健康度** | README 是否完整、License、CI、测试、Issue 响应时长、依赖是否过期（EOL / CVE） | 健康评分 + 缺失清单 |
| **Fork 溯源** | 上游是否存在 / 是否改名 / 是否 archived / 落后多少 commit / 冲突文件 / 上游是否已修过你 fork 修的 bug | 「可回收性」判定 + 行动建议 |
| **独有价值** | 唯一性文件、独有文档、脚本、模板、踩坑记录 | 「余热清单」（可一键导出） |
| **风险** | 泄露的 secrets 扫描（模式匹配，不外传）、依赖漏洞、license 不兼容、敏感信息 | 警告清单 |
| **新鲜度** | 与同类仓库对比（同 topic / 同语言 / 同功能） | 「已被替代」提示 + 替代品推荐 |

#### B. Fork 溯源专项（建议做成独立模块，差异化强）
- 溯源链路图：`你的 fork → direct upstream → root`，标注各自最后活动时间
- 差异面板：ahead / behind commit 数、冲突文件列表、上游 CHANGELOG 摘要
- 自动判定四种状态并给建议：
  - **🟢 上游活跃、我落后** → 建议同步或直接改用上游
  - **🟡 上游已合并我的改动** → 建议删除 fork
  - **🔴 上游死亡** → 建议「转生」：接管为独立项目 / 归档存证
  - **⚪ 我就是 root** → 进入普通诊断流程

#### C. 诊断输出
- **诊断报告页**（可分享 URL）：总评分 + 各维度雷达 + 结论与建议处置动作
- **命令行清单**：把建议动作翻译成可复制的命令（`gh repo archive`、`gh repo rename`、`git bundle`、`rsync` 导出独有文件、`git filter-repo` 提取目录等），标注「需用户手动执行，工具不代跑」
- **导出**：JSON / Markdown / CSV（方便进 Notion、issue、个人 wiki）

---

### 3.4 清理小工具与 Agent Skill（能力输出层）

定位：**把诊断结论变成可执行动作**，但坚持「建议不代劳」。

#### A. Web 端小工具
- 批量归档 / 批量取消 archive / 批量改 visibility（需二次确认 + 影响范围预览）
- 灵龛导出：把选中仓库打包导出（`git bundle` / tar）到本地或云盘
- 独有内容提取：把 docs / scripts / templates 抽出合并到一个「个人碎片仓库」（呼应余热回收）
- 冲突检测：删除前扫描是否有未推送分支、未关闭 PR、未导出的 issue

#### B. Agent Skill / MCP（面向 Copilot / Claude Code / Cursor）
- 提供 `urn.diagnose` / `urn.trace_fork` / `urn.suggest_disposal` / `urn.export_assets` 四个核心工具
- Skill 文档中内置**处置决策树**：agent 根据诊断结果向用户提供建议，所有破坏性动作必须逐条确认
- 所有动作生成「处置凭证」（本地日志 + 可撤销提示），方便审计与回滚
- 安全约束：Skill 默认只读；写操作仅 `archive` / `topic 修改` / `README 加徽章` 三类低风险动作，**不提供 delete**

#### C. 保护机制（必须有）
- 「8 秒冷静期」：执行批量处置前强制倒计时 + 影响清单
- 回收站概念：被处置仓库进入「待遗忘区」30 天，期内一键恢复
- 完全不可逆操作（删除）：**产品内不提供**，只在文档里给出官方命令链接，责任交还用户

### 3.5 社交与传播层

- **用户主页**：`/u/xxx` 展示灵龛、充能数、徽章、处置历史、复活故事
- **分享卡片生成器**：多模板（榜单截图 / 诊断结论 / 年度报告 / 处置勋章），尺寸适配 X、朋友圈、小红书
- **Topic 页作为社区入口**：`urn-of-shadows` topic 本身就是公开广场，产品内嵌「本周新入龛仓库」流
- **UGC**：处置心得、复活故事投稿；优质内容进「回魂录」专栏
- **组织版（B 端延展）**：企业/团队的「仓库资产盘点报告」，含重复建设、技术债可视化，作为商业化抓手
- **开源策略**：核心扫描器开源，榜单与社区闭源运营，降低信任成本

## 4. 信息架构与核心交互流程

```
首页 Landing（玩法说明 + 实时榜单预览 + CTA）
 ├─ 榜单广场 ── 单个榜单 ── 仓库诊断报告页 ── 处置向导 ── 分享卡片
 ├─ 诊断台（输入 repo / 用户名 / 批量）── 诊断报告页 ── 命令清单 / 导出
 ├─ 我的灵龛（登录后）── 灵龛列表 ── 处置向导 ── 处置凭证
 ├─ 清理工具 / Skill 文档
 ├─ 社区「回魂录」── 故事详情
 └─ 设置（榜单可见性 / 隐私 / 通知 / 授权管理）
```

**关键流程 1（轻用户，未登录）**：
看到榜单 → 点进某仓库 → 看到诊断报告 → 点「我也想诊断我的仓库」→ 登录 → 选仓库 → 进灵龛 → 生成分享卡片。

**关键流程 2（重用户，处置）**：
标记 topic → 收到周报 → 批量诊断 → 筛选「建议处置」→ 进处置向导（8 秒冷静期）→ 执行归档/导出 → 充能 +N → 生成徽章 → 分享。

**关键流程 3（Fork 党）**：
输入用户名 → 一键 Fork 溯源 → 看到四种状态 → 点「同步上游 / 删除 fork / 转生」→ 拿到命令清单 → 回填处置结果。

## 5. 合规、信任与风险

| 风险 | 应对 |
|---|---|
| 隐私（私有仓库数据） | 私有数据只做聚合统计，不入库原始内容；单设「隐私模式」一键退出所有榜单 |
| API 限流 | 服务端缓存 + 增量扫描 + 二级数据源（GitHub Archive / GH Archive BigQuery） |
| 被误解为「清理删除工具」 | 首屏明确「不删除、不写入、只读」；删除操作一律外链官方文档 |
| 名字/IP 风险 | 「影之灵龛」仅作灵感来源，UI 不使用 Dota 美术素材，图标需自绘（建议做一个抽象「灵龛 + 充能刻度」符号） |
| 用户被榜单冒犯 | 全局匿名开关、单条目隐藏、举报与下架机制 |
| 数据准确性 | 所有榜单展示「数据更新时间」，允许用户手动触发刷新 |

## 6. 指标体系

- **北极星**：周活跃处置数（用户完成处置决策的仓库数）
- 采集：标记 topic 的仓库数、授权用户数、扫描成功率
- 活跃：周诊断次数、榜单停留时长、回访率
- 价值：处置完成率（诊断 → 处置转化）、导出/命令复制次数、复活率（沉睡仓库重新提交）
- 传播：分享卡片生成数、分享点击回流率、UGC 投稿数、topic 使用量
- 商业（后期）：组织版试用申请、Skill 安装量

## 7. 路线图建议

- **MVP（4–6 周）**：Topic 采集 + 3 个榜单（最长遗弃 / 明珠蒙尘 / 断根之木）+ 单仓库诊断 + 命令清单 + 分享卡片
- **V1**：Fork 溯源专项 + 灵龛与充能系统 + 徽章 + 周报邮件
- **V2**：Agent Skill / MCP + 批量处置向导 + 回魂录社区 + 年度报告
- **V3**：组织版 + 重复建设检测 + 替代品推荐 + 商业化

## 8. 建议你和 PM 现场确认的问题

1. **定位取舍**：工具属性优先还是娱乐传播优先？两者的排序会决定首屏信息架构（我建议：榜单做入口钩子，诊断做留存核心）。
2. **数据边界**：私有仓库是否纳入？这决定 OAuth scope 与用户信任成本。
3. **榜单默认可见性**：默认公开上榜、可退出，还是默认隐藏、需主动加入？（法律与舆论风险点）
4. **处置能力边界**：产品是否要提供任何写操作（archive/rename）？还是完全「只诊断、只给命令」？这决定 Skill 的设计与责任划分。
5. **充能机制的具体数值**：沉睡多少天 = 1 充能？处置动作 = 多少充能？（建议和 Dota 数值做弱绑定，别绑死）
6. **是否做「8 天处置窗口」的紧迫感机制**？对部分用户可能是负体验。
7. **年度报告的时间点**是否要作为主推传播事件？会倒逼数据采集提前上线。
8. **「影之灵龛」命名的对外风险**：是否需要一个更中性的主品牌（如「仓库灵龛 / RepoUrn」）+ 玩梗副标题。
9. **B 端方向**：组织版是否在 V1 就要考虑数据结构（org 维度、权限隔离）？后补成本很高。
10. **成功判定**：MVP 三个月后，什么信号说明这个产品该继续投入？（建议提前定好，避免被日活绑架）
