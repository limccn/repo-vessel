# GitHub 沉睡仓库产品竞品分析

> **调研结论：有类似产品，而且有一个与你的设想非常接近。**  
> 其中，VibeCemetery 已经把「扫描不活跃仓库、墓地隐喻、骨灰盒、社区榜单、分享和 Agent 指令」组合在了一起。你的机会不在于抢占“仓库墓地”概念，而在于把重点转向：**帮助用户安全地整理仓库，尤其是做出有依据的 Fork 处理决策。**

**调研时间：2026 年 10 月 30 日。**  
本报告基于公开网站、GitHub README 和 GitHub 官方文档。部分判断来自产品自述或页面展示，未逐一完成登录、授权和真实仓库操作；对于没有看到的功能，仅表述为“未在公开资料中确认”，不视为绝对不存在。

---

## 一、核心发现

### 1. 这个需求确实有人在做

现有产品大致分为四类：

| 类别 | 代表产品 | 主要解决什么问题 |
|---|---|---|
| 仓库墓地与社交 | VibeCemetery、GitHub Graveyard | 给沉睡项目一个可分享的故事或社区空间 |
| 仓库复活与 AI 诊断 | Museum of Dead Dreams、Lazarus | 分析旧项目，生成继续开发的计划 |
| 个人仓库清理 | GitHub Stale Fork Manager、repjan | 找出不活跃仓库，辅助归档或删除 |
| 组织仓库治理 | Stale Repos Action | 批量识别组织中需要考虑归档的仓库 |
| 沉睡项目发现 | CodeFossils | 从社区中发现可能值得重新挖掘的项目 |

### 2. 最接近你的不是传统清理工具，而是 VibeCemetery

它已经具备以下组合：

- GitHub 登录和仓库扫描；
- 沉睡仓库入葬；
- 墓碑、骨灰盒和墓志铭；
- 社区榜单；
- 可分享链接与社交卡片；
- 本地 Agent `/bury` 命令。

这意味着：**“用墓地或骨灰盒隐喻沉睡仓库”已经不是独有创意。**

但它当前明确排除 Fork，而你的设想恰好把 Fork 溯源作为重点。这是一个值得验证的差异点。

### 3. 你的方案仍有产品空间，但需要重新定义主张

建议不要把产品定位为：

> 一个有榜单的 GitHub 仓库墓地。

而是：

> **一个帮助开发者判断“旧仓库该保留、归档还是唤醒”的个人整理工具，同时让用户自愿分享值得留下的项目故事。**

其中最值得优先验证的是：

> **安全、只读、可解释的 Fork 整理。**

### 4. 先修正一个关键预期

无论是你的产品还是竞品，都不能因为在第三方网站给仓库打了标记，就让 GitHub 仓库真正从 GitHub 所有列表中消失。

GitHub 自带归档功能，但归档的含义是将仓库设为只读、表明不再积极维护；归档仓库仍然可以被搜索，也可以取消归档。参见 [GitHub 官方归档说明](https://docs.github.com/en/repositories/archiving-a-github-repository/archiving-repositories)。

所以产品应解决的是：

- 帮用户**做决定**；
- 在本站提供一个更清晰的仓库视图；
- 在用户明确确认后，辅助执行 GitHub 原生操作；

而不是承诺“替你从 GitHub 隐藏仓库”。

# 三、重点竞品分析

## 1. VibeCemetery：与你的创意最接近

**产品链接：**[GitHub 项目](https://github.com/azkian1/VibeCemetery) · [产品网站](https://vibecemetery.app/)

### 它在做什么

VibeCemetery 将未完成、被搁置的软件项目放进一个公共数字墓地。

公开 README 描述的主要流程是：

1. 用户使用 GitHub 登录；
2. 扫描自己账号下的仓库；
3. 选择不活跃仓库；
4. 写下“死亡原因”；
5. 将项目放进像素墓地，或以骨灰形式记录；
6. 分享仓库墓碑或骨灰盒链接。

它还提供：

- 可探索的像素墓地；
- 搜索墓志铭的档案区；
- 社区榜单；
- “Press F”致敬；
- 社交分享卡片；
- 面向本地项目的 Agent 命令 `/bury`。

### 与你的重合度

| 你的设想 | VibeCemetery 的公开资料 |
|---|---|
| GitHub 扫描 | 已有 |
| 沉睡仓库隐喻 | 已有，使用墓地和死亡意象 |
| 骨灰盒概念 | 已有 urn / cremation |
| 榜单 | 已有社区活动相关榜单 |
| 分享 | 有链接和社交卡片 |
| Agent Skill | 有面向本地项目的 `/bury` |
| Fork 整理 | 当前入葬流程排除 Fork |

**特别注意：**它的 `/bury` 面向本地项目文件夹，不等于它已经提供 GitHub Fork 清理 Agent。另外，其更广义的 Agent Layer 在 README 中被标为暂停，不应把历史代码当成当前产品功能。

### 值得借鉴

- 仪式感很强，用户容易理解“为一个项目画句号”；
- 分享内容不是冰冷的数据表，而是有叙事的项目卡片；
- 只扫描登录用户自己的账号，并在服务端验证仓库所有权，降低了冒名展示他人仓库的风险。

### 你的潜在差异

1. **支持 Fork，而不是过滤 Fork。**
2. **不仅提供结束仪式，还提供“保留、归档、唤醒、暂不处理”的决策。**
3. **解释建议依据，而不是只使用“项目死亡”的叙事。**
4. **让社区展示成为可选结果，而不是整理仓库的前提。**

**判断：**这是你上线前最需要持续跟踪的直接竞品。

## 2. Museum of Dead Dreams：情绪化包装 + AI 复活

**产品链接：**[GitHub 项目](https://github.com/jpablortiz96/Museum-of-Dead-Dreams) · [项目列出的在线体验](https://osiam2phyuryk.kimi.page)

### 它在做什么

用户输入 GitHub 用户名后，产品分析公开仓库，把沉睡项目变成“博物馆展品”，再生成：

- 项目档案；
- 基于仓库信息的叙事；
- AI 问答；
- 复活计划；
- Markdown 或 PDF 报告；
- GitHub Copilot 可使用的指令和 Skill 文件。

它的公开资料称，博物馆生成过程会过滤 Fork。

### 值得借鉴

它将结果从“这个仓库很久没有更新”推进到了：

> “如果你想继续做，下一步可以从哪里开始？”

尤其值得参考的是：**把诊断结果交给 Agent 的交接格式**。项目展示的资料包包含计划、待办和 Agent 指令，而不仅是一段聊天回答。

### 产品风险

这类产品会推测项目“为什么失败”或“是否有市场价值”。这些问题很难仅通过仓库元数据可靠判断。

你的产品可以有所区别：

- 将“事实”和“推测”分开；
- 不把缺少提交直接解释为失败；
- 不默认用户需要复活项目；
- 对无法判断的部分直接标注“需要你确认”。

### 对你的启发

你的 Agent Skill 不一定首先生成“复活计划”，也可以生成更适合当前问题的：

> **仓库整理计划：现状、风险、建议动作、待确认事项。**

## 3. Lazarus：低门槛的免登录体验

**产品链接：**[GitHub 项目](https://github.com/chintanonweb/lazarus)

### 它在做什么

Lazarus 允许用户输入 GitHub 用户名，查看公开仓库的“墓地”，并提供：

- 不活跃程度评分；
- 墓志铭；
- 可下载的年度总结式分享卡；
- 复活检查清单；
- GitHub Copilot 指令和提示词。

其 README 将产品描述为免登录、无后端的体验；同时提到可选只读 PAT，用于私有仓库和提高 API 请求额度。

### 值得借鉴

**先体验，再授权。**

用户只需输入用户名，就能看见自己的公开仓库概览，不必在第一次访问时做授权决定。

你的网站可以采用类似的分层：

```text
输入 GitHub 用户名
→ 预览公开仓库概况
→ 用户认为有用
→ 再登录以保存个人状态或验证所有权
```

### 需要注意

- 公开仓库可被读取，不等于作者同意被公开展示；
- 输入任意用户名查看公开信息，与把某人放上公开榜单是两回事；
- 不建议让普通用户直接粘贴长期有效的 Token 到网站。

## 4. GitHub Graveyard：社区互动与项目再发现

**产品链接：**[GitHub 项目](https://github.com/nacosof/github-graveyard) · [产品网站](https://gitgrave.com/)

### 它在做什么

根据项目 README，用户可以：

- 粘贴仓库链接，查看项目快照；
- 将项目标记为 `abandoned`、`finished`、`underrated`；
- 在分类空间里发现项目；
- 给项目“点蜡烛”，帮助其获得关注。

### 与你的区别

它更偏向：

> **社区发现与评价项目。**

而你的核心用户首先是仓库所有者：

> **我该如何整理自己的仓库？**

### 值得借鉴

“点蜡烛”比简单的点赞更有主题感。你可以考虑类似的轻互动，但不必照搬墓地叙事。

例如：

- `点亮余烬`：表示这个仓库对我有帮助；
- `收藏灵感`：把项目保存到自己的参考列表；
- `留下回响`：写一句这个项目对自己的帮助。

### 风险

如果允许任何人把他人的仓库标记为“已死”或“被遗弃”，可能对维护者造成误解。

建议：

- 榜单默认只收录所有者主动参与的仓库；
- 尽量用客观状态，例如“多久没有推送”；
- 不让陌生用户替作者填写“死亡原因”。

## 5. CodeFossils：沉睡仓库发现与排序

**产品链接：**[CodeFossils](https://www.codefossils.com/)

### 它在做什么

CodeFossils 将旧项目比喻为“代码化石”，面向希望发现和重新利用旧项目的用户。

本次访问其首页时，页面展示：

- 项目目录；
- Star、Fork、语言、最近活跃时间等信息；
- `Latest`、`Best Ideas`、`Most Stars`、`Most Stale` 等浏览方式；
- 页面显示约 4,921 个条目。

这个数字只是页面访问时的快照，不能直接等同于真实用户数、有效项目数或市场规模。

### 值得借鉴

它证明了一种可理解的浏览体验：

> 旧项目不只是需要被清理，也可能值得被发现。

你的“余烬榜”可以借鉴：

- 长期无推送，但仍有 Star；
- 长期无推送，但有人 Fork；
- 用户主动标记“欢迎参考”的仓库。

### 你的差异化

CodeFossils 的公开页面更偏向“发现别人的项目”；你的产品可以从“整理自己的项目”出发，再由所有者决定哪些项目值得公开。

## 6. GitHub Stale Fork Manager：最直接的 Fork 工具竞品

**产品链接：**[GitHub 项目](https://github.com/albrektsson/gh-dashboard)

### 它在做什么

这是一个专门处理不活跃 Fork 的 Web 工具，公开 README 列出的功能包括：

- 可配置不活跃时间；
- 筛选公开、私有和归档状态；
- 查看 Fork 的来源；
- 批量归档；
- 批量删除；
- OAuth 或个人访问令牌认证。

项目示例中的 OAuth 权限包含 `repo` 和 `delete_repo`，因为产品支持修改和删除仓库。

### 与你的直接竞争

它已经覆盖你想做的一部分：

> 找到长期不活跃的 Fork，并帮助用户处理。

所以，仅有“扫描 Fork + 批量归档”不足以形成明显差异。

### 你的机会

可以把重点放在它的批量操作之前：

1. 这个 Fork 是否有自己的改动？
2. 上游是否仍然存在、活跃或已归档？
3. 这个 Fork 是否只是收藏用途？
4. 用户是否明确不再需要继续开发？
5. 归档前是否有未处理事项？

建议产品强调：

> **先帮助用户理解，再决定是否操作。**

并且第一版默认只读；如果未来支持写操作，单独申请权限，而不是为了扫描一开始就申请删除权限。

## 7. repjan：终端用户的批量整理工具

**产品链接：**[GitHub 项目](https://github.com/llbbl/repjan)

### 它在做什么

repjan 是一个终端界面工具，可以：

- 查看个人或组织仓库；
- 按时间、Star、Fork、语言筛选；
- 识别可能适合归档的仓库；
- 批量标记和归档；
- 导出 JSON 清单。

### 值得借鉴

- 为仓库整理提供高密度、可批量处理的视图；
- 让用户能够导出处理清单，而不被绑定在某个 UI 中。

### 需要避免

其 README 中的部分启发式规则会把某些语言与“不活跃”组合起来判断归档候选。这种规则可能引发误判。

你的产品更适合使用用户容易理解的证据：

- 最后推送时间；
- 是否有独立修改；
- 上游状态；
- 是否已经归档；
- 用户自行设置的保留标签。

不要因为语言“老”、Star 少，就断定仓库没有价值。

## 8. Stale Repos Action：成熟的仓库治理参考

**产品链接：**[GitHub 项目](https://github.com/github-community-projects/stale-repos/)

### 它在做什么

这是由 GitHub 开发并开源的 Action，用于识别长期没有活动的仓库，生成报告，供维护者考虑归档。

它主要面向组织治理，也可以在特定配置下扫描 Token 所有者的仓库。

支持：

- 自定义不活跃天数；
- 按最后推送或默认分支更新判断活动；
- 使用 Topic 或仓库名排除特定项目；
- 输出报告；
- 补充 Release、Pull Request 等指标。

### 最值得借鉴的不是 UI，而是数据口径

“最后推送”和“默认分支最后提交”是不同概念：

- 自动化工具可能产生推送；
- 其他分支活动不一定代表主要项目仍在维护；
- 稳定、完成的项目也可能长期没有提交。

你的诊断界面应明确告诉用户：

> **这个仓库多久没有推送**，不等于**作者多久没有工作**，也不等于**项目已经失效**。

# 四、竞争格局：你的产品应该站在哪里？

可以用两个维度理解现有产品：

```text
                    更偏社区与表达
                          ↑
                          │
           VibeCemetery   │   GitHub Graveyard
                          │   CodeFossils
                          │
     Museum of Dead Dreams│
             Lazarus      │
                          │
──────────────────────────┼────────────────────────→ 更偏工具与治理
                          │
                          │   GitHub Stale Fork Manager
                          │   repjan
                          │   Stale Repos Action
                          │
```

### 你的目标位置

建议站在两个方向的交叉点，但不要一开始平均发力：

```text
核心：个人仓库整理和决策
                  +
亮点：可选择的项目故事与社区分享
```

也就是说：

- 用户即使不分享，也应该能完成一次有价值的整理；
- 用户即使不归档，也可以只做一次回顾和分类；
- 愿意分享时，产品再把结果转成有趣的卡片或榜单。

# 五、你的产品与竞品相比，有哪些机会？

## 机会一：把 Fork 当作第一优先级

这是本次调研中最明确的产品切口。

- VibeCemetery 当前排除 Fork；
- Museum of Dead Dreams 公开说明中过滤 Fork；
- GitHub Stale Fork Manager 重视清理，但公开资料的重点是识别和批量操作。

你可以把产品做成：

> **帮你理解那些曾经 Fork、却不记得为什么 Fork 的仓库。**

### 可以回答的问题

| 用户问题 | 可能使用的证据 |
|---|---|
| 这是从哪里 Fork 的？ | GitHub 提供的来源仓库信息 |
| 上游还存在吗？ | 上游是否可访问 |
| 上游还活跃吗？ | 最后推送时间、归档状态 |
| 我做过自己的修改吗？ | 在具备条件时比较分支或提交差异 |
| 它有没有人关注？ | Star、Fork 等信号 |
| 我应该怎么处理？ | 结合上述证据给出选项，不自动决定 |

**注意：**这些信号并不总能完整取得。上游不可访问不一定是被删除；分支无法比较也不等于没有修改。

---

## 机会二：从“死亡判决”改为“有依据的选择”

很多竞品采用“死亡”“失败”“墓碑”“复活”等叙事，容易传播，但有时会给用户错误暗示：

- 一个完成的项目可能无需更新；
- 一篇论文代码可以长期保持稳定；
- 一个 Fork 可能只是为了保存阅读入口；
- 用户可能不想复活，也不想删除。

你的产品可以提供四种平等的结局：

1. **继续维护**
2. **保留现状**
3. **正式归档**
4. **暂时不决定**

产品不应该暗示“复活”才是最好的选择。

---

## 机会三：把只读和安全做成产品承诺

对于仓库清理工具，权限本身就是体验的一部分。

建议把产品承诺写在首屏：

> **默认只读。不会自动删除、归档或修改你的仓库。**

再做权限分层：

| 场景 | 建议方式 |
|---|---|
| 预览公开仓库 | 输入用户名即可尝试，视 API 限制处理 |
| 保存本站整理状态 | GitHub 登录，验证用户身份 |
| 扫描私有仓库 | 单独申请所需读取权限 |
| 归档或修改仓库 | 用户前往 GitHub，或后续单独授权写操作 |
| 删除仓库 | 第一版不提供自动删除 |

具体授权方案需由开发根据 GitHub App、OAuth 与实际 API 重新核对，不能只在文案上承诺“只读”。

---

## 机会四：从“社交墓地”转向“自愿分享余热”

你的品牌不必与 VibeCemetery 在墓地氛围上正面竞争。

可以更强调：

> **这个项目虽然安静了，但它留下的代码、知识或故事仍然有用。**

分享卡可以从“项目死了多久”转向：

- 我从这个项目学到了什么；
- 这个 Fork 曾帮我解决什么问题；
- 项目停在什么阶段；
- 是否欢迎他人参考或继续探索。

这样可以同时降低羞辱感，增加真实内容。

---

## 机会五：把 Agent 用在“安全整理”，而非默认复活

现有竞品已经有 Copilot 复活计划和本地 Agent 命令，因此“支持 Agent”本身也不是差异点。

更具体的机会是：

> **生成一个可审查、可确认、可回退的仓库整理计划。**

例如：

```text
仓库：alice/example-fork

已知事实：
- 该仓库是 Fork
- 最近 18 个月未检测到推送
- 上游可访问，且最近 3 个月有推送
- 当前比较结果：无法确认是否存在独立修改

建议：
- 先查看分支差异
- 如只是收藏用途，可以在本站标记为“保留参考”
- 如确认不再维护，可考虑在 GitHub 归档

待用户确认：
- 是否查看 GitHub 上游？
- 是否生成归档命令？

自动执行：
- 无
```

这比让 Agent 直接“帮我清理所有旧仓库”更容易建立信任。

---

# 六、对原方案的调整建议

## 1. 产品名称与视觉：可以保留灵感，但不宜只靠它区分

你原本的“影之灵龛 / 骨灰盒”与 VibeCemetery 的 urn、cremation 概念有明显重叠。

这不意味着不能继续使用，但建议：

- 品牌重点放在“余烬、安放、选择”，而不是“埋葬”；
- 使用原创视觉，不依赖游戏装备图标；
- 上线前单独做名称、域名、商标与素材权利检索；
- 不把“第一个仓库骨灰盒”作为传播主张。

## 2. 首页：先体验，再登录

建议首页主要流程调整为：

```text
输入 GitHub 用户名
→ 预览公开仓库的沉睡概况
→ 展示可解释的整理建议
→ 登录后保存个人处理状态
→ 自愿选择是否公开分享
```

这样比首屏直接要求 GitHub 授权更容易让新用户理解价值。

但要明确：

- 免登录预览仅针对公开数据；
- 任意用户名的预览不自动进入公开榜单；
- 公开参与仍需验证所有权或采用清晰的自愿机制。

## 3. 榜单：从“最长遗弃”改成“沉睡与余热”

建议保留趣味性，但调整命名：

| 原方向 | 建议名称 | 理由 |
|---|---|---|
| 最长遗弃榜 | 最长沉睡榜 | 避免直接评价作者 |
| 长期没人维护但 Star 高 | 余烬未熄榜 | 更符合产品叙事 |
| 长期未更新但近期被 Fork | 仍在传承榜 | 强调继续被使用 |
| 长期沉睡后更新 | 唤醒故事 | 强调用户主动选择 |

榜单必须写明数据来源、统计口径和更新时间。

## 4. 分享：主人自己讲故事

建议让用户填写：

> “我想把这个仓库留下来，因为……”

而不是让 AI 自动生成：

> “这个项目因为作者失去兴趣而死亡。”

前者来自当事人，后者往往缺乏证据。

## 5. Agent：先生成清单，后考虑执行

第一版可只提供：

- Markdown 整理报告；
- JSON 导出；
- Agent 提示词或 Skill 说明；
- 命令预览。

暂不做：

- 自动删除；
- 自动批量归档；
- 自动修改 Topic；
- 自动同步上游 Fork。

这样能避免为了一个尚未验证的需求，过早引入高权限和操作风险。

# 七、建议的 MVP 与竞品对位

## MVP 一句话

> **输入 GitHub 用户名，看看哪些仓库值得重新决定；登录后，把它们安全地安放或分享。**

## MVP 功能

| 优先级 | 功能 | 主要对位 |
|---|---|---|
| P0 | 公开仓库免登录预览 | 降低首次体验门槛 |
| P0 | 沉睡时间筛选 | 基础整理能力 |
| P0 | Fork 来源与上游状态 | 针对直接竞品的明显切口 |
| P0 | 只读诊断与依据展示 | 建立信任 |
| P0 | GitHub 登录后保存本站状态 | 让整理结果可持续 |
| P1 | 自愿生成仓库故事卡 | 传播 |
| P1 | 用户主动加入沉睡榜 | 社区冷启动 |
| P1 | 导出整理清单 | 对接 Agent 或用户工作流 |
| P2 | 私有仓库独立授权 | 扩大适用范围 |
| P2 | Fork 分支差异深度分析 | 提高决策质量 |
| P2 | Agent Skill | 将计划交给用户的本地 Agent |
| P3 | 写操作授权与执行 | 需求验证后再做 |

### 一个关键修订

之前方案中提到可以通过给仓库添加 Topic 加入社区。调研后建议**不要把 Topic 作为唯一入口**：

- 给仓库添加 Topic 本身是写操作；
- 用户可能不愿意为了参与榜单修改仓库；
- GitHub 搜索发现不一定实时或完整；
- Topic 的存在也需要被解释为一种明确的公开参与信号。

更直接的第一版流程是：

> 用户登录 → 选择自己的公开仓库 → 预览内容 → 同意公开。

Topic 可作为后续补充发现方式，而非 MVP 核心。

# 八、建议优先验证的产品假设

目前竞品存在，只能证明“有人尝试解决这个问题”，**不能证明用户规模、付费意愿或需求强度**。建议先做小范围验证。

| 假设 | 如何验证 | 值得观察的信号 |
|---|---|---|
| 用户确实想整理旧仓库 | 邀请 10–15 名仓库较多的开发者访谈或试用 | 是否能说出具体困扰，而不只是觉得概念有趣 |
| Fork 整理是高频痛点 | 观察用户扫描后的 Fork 列表 | 用户是否主动打开上游和差异信息 |
| 只读会提高信任 | 对比权限文案或询问试用者 | 用户是否因为权限而停止使用 |
| 分享卡有传播价值 | 让用户预览并自主分享 | 实际分享，而不仅是口头喜欢 |
| 用户需要 Agent 整理清单 | 提供手工导出原型 | 用户是否复制、下载或带入自己的工具 |

这些数量是**建议的探索规模**，不是市场统计结论。

### 最值得观察的行为

不要只看“有多少人扫描了仓库”。更重要的是：

> 用户看完诊断后，是否真的为至少一个仓库做出了决定？

例如：

- 标记保留；
- 标记忽略；
- 计划唤醒；
- 前往 GitHub 查看；
- 选择归档；
- 主动分享。

# 九、最终判断

## 是否值得做？

**值得继续验证，但不建议把“仓库墓地 + 榜单”本身当成差异化。**

现有产品已经覆盖了：

- 沉睡仓库扫描；
- 墓地和骨灰盒意象；
- 社交分享；
- 榜单；
- AI 复活计划；
- Agent 相关能力；
- 批量 Fork 清理。

你的新产品需要在这些基础上，给出更聚焦的答案。

## 最推荐的差异化主张

> **影之灵龛：帮你整理 GitHub 上沉睡的仓库，尤其是那些不知该如何处理的 Fork。默认只读，先理解，再决定；想分享时，让旧代码的余热被看见。**

如果只能先做一个真正有竞争力的功能，我建议是：

> **Fork 溯源与整理决策面板。**

因为它同时连接了用户的真实管理问题、竞品之间的功能空隙，以及你最初提出的“不想看到，但也不想删除”的核心矛盾。
