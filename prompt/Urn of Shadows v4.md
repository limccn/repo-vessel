# 影之灵龛 Urn of Shadows · 产品设计 v4.0

> **给沉睡的公开仓库，一个轻一点的归宿。**

## 一、这次版本的核心变化

v4 不再把影之灵龛设计成一个需要用户持续参与的社区，也不要求用户养成整理习惯。

产品只围绕三个真实、简单的动作：

1. **用户手动给仓库添加 `urn-of-shadows` Topic；**
2. **用户输入 GitHub 用户名，或使用 GitHub 登录，查看自己的公开仓库；**
3. **用户认领已被收录的公开仓库，管理它在本站的展示方式。**

用户可以只做其中一件事，不需要完成一整套流程。

### 本版产品边界

- **只处理个人账户拥有的公开仓库；**
- **不扫描、不授权、不读取私有仓库；**
- **不扫描、不读取组织仓库；**
- 网站默认只读，不修改 GitHub 仓库；
- 不提供删除、归档、同步、改名等站内写操作；
- 不做社区互动、打卡、提醒和养成机制。

---

# 二、产品定位

## 2.1 一句话定义

> **影之灵龛是一个轻量的 GitHub 公开仓库整理与发现工具：帮你找到沉睡仓库、看清 Fork 的来路，并自行决定是否将它们展示在灵龛中。**

## 2.2 它解决什么问题

| 用户问题 | 产品提供的帮助 |
|---|---|
| “我的仓库太多，不知道哪些已经很久没动。” | 输入用户名，快速筛选公开仓库 |
| “这个 Fork 当初从哪里来的，上游现在怎么样？” | 在允许的范围内展示来源与上游状态 |
| “我不想删除，但想把它标记为暂时放下。” | 手动添加 Topic，或在本站认领后管理展示 |
| “我想看看别人的沉睡项目。” | 浏览由个人所有者通过 Topic 主动标记的公开仓库 |
| “我不想自己的仓库继续出现在这里。” | 登录认领后隐藏；Topic 入库的仓库也可移除 Topic |

## 2.3 它不解决什么问题

- 不会让仓库从 GitHub 原生仓库列表中消失；
- 不代替用户清理、归档或删除仓库；
- 不判断某个仓库“是否有价值”；
- 不监控用户是否持续提交；
- 不处理私有仓库和组织仓库。

---

# 三、与竞品的差异化

基于前一轮竞品调研，本版不再强调“大而全”的功能，而聚焦一个更轻的体验。

| 竞品方向 | 常见做法 | 影之灵龛 v4 |
|---|---|---|
| 仓库墓地 | 登录、入葬、写墓志铭、参与互动 | 添加 Topic 即可表达“安放”，不要求写故事 |
| 仓库清理工具 | 授权后批量归档或删除 | 默认只读，提供信息，不替用户操作 |
| AI 复活工具 | 生成复活计划或项目叙事 | 不要求复活，只展示可核实的仓库事实 |
| 社区发现产品 | 用户互动、点赞、投稿 | 只有轻量榜单和分享，不做社区 |
| Fork 管理工具 | 重点处理批量 Fork | 在轻量预览中提供 Fork 来源与上游状态 |

**真正的产品差异不是功能数量，而是使用成本：**

> 不需要安装 App，不需要授权仓库写权限，不需要持续回来，也不需要把仓库交给产品处理。

# 四、三个核心入口

## 入口一：手动添加 Topic

### 用户行为

用户在自己的**个人公开仓库**中手动添加：

```text
urn-of-shadows
```

### 产品行为

产品定期通过 GitHub 的公开信息发现带有该 Topic 的仓库，并尝试将符合条件的仓库收录到榜单。

### 用户体验

```text
在 GitHub 给仓库添加 Topic
        ↓
等待产品发现并更新
        ↓
仓库出现在公开灵龛 / 榜单
```

用户不需要先登录影之灵龛。

### 需要明确告诉用户

- 添加 Topic 是用户在 GitHub 上自行执行的修改；
- Topic 是公开信息，产品会将其作为**允许公开收录的信号**；
- 由于 GitHub 搜索索引、分页和限流等因素，收录可能延迟，也不保证发现全部符合条件的仓库；
- 用户可以移除 Topic，也可以登录本站认领后隐藏。

**建议在页面提供一个“检查收录状态”输入框。** 用户粘贴仓库 URL 后，产品检查它是否公开、属于个人账户、是否带有 Topic，以及当前是否已收录。不符合条件时给出原因。

---

## 入口二：输入用户名或 GitHub 登录

### 方式 A：输入 GitHub 用户名

用户输入用户名后，产品读取该个人账户拥有的公开仓库，提供一次轻量预览。

```text
输入用户名
    ↓
查看公开仓库概览
    ↓
按沉睡时间 / Fork / Star 筛选
    ↓
查看单个仓库的基础信息
```

**重要区别：**输入用户名只是查看公开数据，**不会自动将这些仓库收录到公开榜单**。

### 方式 B：GitHub 登录

用户登录后，可以：

- 更方便地查看自己拥有的公开仓库；
- 认领本站已收录、且当前属于自己的仓库；
- 隐藏或恢复自己仓库在本站的展示；
- 撤回本站保存的认领及展示设置。

登录不等于仓库写授权，不能修改仓库。

### 用户名输入与登录的关系

| 能力 | 输入用户名 | GitHub 登录 |
|---|---|---|
| 查看符合范围的公开仓库 | 可以 | 可以 |
| 查看基础沉睡状态 | 可以 | 可以 |
| 查看 Fork 基础信息 | 可以 | 可以 |
| 管理本站展示状态 | 不可以 | 可以 |
| 认领仓库 | 不可以 | 可以 |
| 修改 GitHub 仓库 | 不可以 | 不可以 |

---

## 入口三：认领已收录仓库

### 为什么需要认领

产品可能通过公开 Topic 发现仓库。认领的作用是让仓库所有者对**本站如何展示该仓库**拥有管理权，而不是向产品授予仓库控制权。

### 认领流程

```text
在榜单或仓库详情中点击「这是我的仓库」
        ↓
GitHub 登录
        ↓
系统验证：登录账户是否为仓库当前个人所有者
        ↓
认领成功
        ↓
管理本站展示状态
```

### 认领后可以做什么

- 隐藏仓库；
- 恢复展示：仓库仍公开、仍属于该用户，且满足本站收录条件时可恢复；
- 查看当前展示的数据和更新时间；
- 移除自己的本站管理记录；
- 获取移除 Topic 的 GitHub 操作指引。

### 认领后不能做什么

- 修改仓库内容；
- 修改 Topic；
- 更改仓库可见性；
- 归档、删除或同步仓库；
- 认领其他个人用户或组织拥有的仓库。

### 所有权变化

每次进行认领或修改展示状态时，产品都需要重新确认：

- 仓库仍可公开访问；
- 当前所有者是个人账户；
- 登录用户是当前所有者。

仓库如果转移给其他所有者，旧所有者的管理权应失效；转入组织、变为私有或无法确认状态时，应从公开展示中移除或暂时隐藏。

# 五、数据范围与公开规则

## 5.1 只处理什么

| 仓库类型 | 是否处理 |
|---|---|
| 个人账户拥有的公开仓库 | 是 |
| 个人账户拥有的私有仓库 | 否 |
| 组织拥有的公开仓库 | 否 |
| 组织拥有的私有仓库 | 否 |
| 用户作为协作者参与、但不拥有的仓库 | 不作为“我的仓库”处理 |

## 5.2 用户名预览与公开榜单的区别

| 来源 | 用途 | 自动公开上榜？ |
|---|---|---|
| 用户输入用户名 | 当次预览该个人账户的公开仓库 | 否 |
| 用户登录 | 查看自己的公开仓库、认领和管理 | 否 |
| 个人公开仓库带有指定 Topic | 作为自愿公开收录信号 | 符合条件且被发现后，可收录 |
| 仓库所有者在本站隐藏 | 管理本站展示 | 否，隐藏优先 |

这样既保留 Topic 的轻交互，也避免因为有人搜索了某个用户名，就把这个人的所有公开仓库放上榜单。

## 5.3 仓库退出收录

用户有两种方式：

1. **在 GitHub 移除 Topic**：产品下次核实到 Topic 已移除后下架；
2. **登录本站认领并隐藏**：隐藏后停止公开展示，即使 Topic 尚未移除，也不会因下一次扫描重新出现。

第二种情况需要保存一条最小化的“禁止展示”记录，避免系统反复重新收录。产品应告知用户保存了什么、如何删除。

### 更新与失效规则

- 展示数据时标注最近核实时间；
- 定期重新核实仓库是否公开、属于个人账户、仍有 Topic；
- 如果已知仓库不再符合条件，立即从公开页面下架；
- 如果重新核实时无法确认状态，应暂时隐藏，而不是继续假定它仍然公开；
- 榜单页面需提示：GitHub 搜索发现和状态同步存在延迟。

这些措施可以降低误展示风险，但无法保证第三方已经保存的截图、缓存或转发内容被完全删除。

## 7.2 仓库预览结果

### 顶部概览

展示本次读取到的数据：

- 公开仓库数量；
- 超过 1 年未推送的仓库数量；
- Fork 数量；
- 已归档仓库数量。

**说明：**概览基于本次成功读取的仓库；如果受到分页或限流影响，必须提示结果可能不完整。

### 仓库列表

每张卡片展示：

- 仓库名和简介；
- `原创` / `Fork`；
- 主要语言；
- Star / Fork 数；
- 最后推送时间；
- GitHub 是否已归档；
- 是否带有 `urn-of-shadows` Topic；
- `查看详情`、`打开 GitHub`。

### 筛选和排序

**筛选：**

- 全部 / Fork / 原创；
- 沉睡 6 个月、1 年、3 年以上；
- 已归档 / 未归档；
- 是否带有指定 Topic。

**排序：**

- 最后推送时间；
- Star 数；
- Fork 数；
- 创建时间。

第一版不提供无法稳定取得的排序项，不用“未知”冒充零。

# 八、Fork 溯源：保留最有价值的轻量能力

## 8.1 第一版展示什么

对于个人公开 Fork，展示 GitHub 能提供且符合产品范围的信息：

- 是否为 Fork；
- 来源仓库名称和链接，若可展示；
- 来源是否可访问；
- 来源是否已归档；
- 来源最后推送时间，若可读取；
- 双方比较是否可用；
- 在条件允许时，展示指定分支的领先 / 落后提交数。

## 8.2 组织仓库边界

如果 Fork 的上游属于组织账户：

- **不进一步读取或扫描该组织仓库；**
- 在个人 Fork 的公开元数据已提供来源名称或链接时，可以只展示这条已有的来源线索；
- 上游活跃状态、归档状态和分支比较显示为：`上游属于组织仓库，本站不读取`。

如果产品希望采取更严格的口径，也可以连组织来源名称都不展示；这是上线前需要确定的细节。无论哪种方式，都不对组织仓库发起进一步扫描。

## 8.3 状态文案

| 情况 | 展示 |
|---|---|
| 个人上游可访问 | 展示来源及可获得的基础状态 |
| 个人上游已归档 | `上游已归档` |
| 上游不可访问 | `无法访问上游，无法确认其状态` |
| 上游属于组织 | `上游属于组织仓库，本站不读取` |
| 分支无法比较 | `当前无法比较双方分支` |
| 当前仓库不是 Fork | 不展示 Fork 溯源模块 |

### 不做自动结论

不显示：

- “上游已经修复，可以删除”；
- “你的 Fork 没有价值”；
- “你的所有修改都已经合并”；
- “上游已死”。

产品只提供事实与限制，最终决定交给用户。

# 九、榜单：保留趣味，去掉社区

## 9.1 榜单收录范围

只展示：

- 属于个人账户的公开仓库；
- 带有 `urn-of-shadows` Topic；
- 已被产品发现并完成最近一次有效核实；
- 未被当前所有者在本站隐藏。

榜单不是全 GitHub 的完整排名，而是：

> **在本站已发现并符合条件的仓库中进行排序。**

## 9.2 第一版三个榜单

### A. 最长沉睡榜

**定义：**按最后推送时间从早到晚排序。

**卡片示例：**

```text
#12  alice / old-project

已沉睡约 1,024 天
⭐ 128  ·  Fork 23

最后推送：2024-01-10
[查看详情] [打开 GitHub]
```

### B. 明珠蒙尘榜

**定义：**长时间未推送，但仍获得一定 Star 的仓库。

**默认排序：**Star 数从高到低。

**文案：**

> 它们很安静，但仍有人记得。

### C. Fork 时光差榜

**定义：**上游为个人公开仓库，且双方指定分支可比较的 Fork。

**默认排序：**相对上游落后的提交数。

**说明：**

- 明确比较的分支；
- 展示比较时间；
- 落后提交数不等于项目需要同步；
- 无法比较的仓库不进入该项排序。

## 9.3 通用筛选

- 语言；
- 原创 / Fork；
- 沉睡时长；
- 是否已归档。

## 9.4 不做的榜单与互动

不做：

- 用户充能榜；
- 判官榜、义工榜；
- 沉没成本工时榜；
- 自动“召唤”仓库所有者；
- 点赞、上香、评论、投票；
- 故事投稿和社区广场。

榜单的作用是**发现和轻量分享**，不是要求用户参与运营。

# 十、分享：只保留最轻的一步

每个公开榜单条目提供：

- `复制链接`
- `生成分享卡片`

### 分享卡片内容

- 仓库名称；
- 所有者；
- 最后推送时间；
- 沉睡时长；
- Star / Fork；
- 数据更新时间；
- 产品名称。

### 示例文案

> 这个公开仓库已经安静了 1,024 天。  
> 在影之灵龛看看它。

### 规则

- 不自动 @ 所有者；
- 不自动发布到任何平台；
- 不生成“失败”“浪费了多少小时”等结论；
- 卡片生成前提供预览；
- 若仓库被隐藏或下架，其本站公开链接应停止展示。

# 十一、保留哪些“影之灵龛”元素？

## 保留

- 名称和抽象灵龛视觉；
- `沉睡`、`余烬`、`入龛`等轻量隐喻；
- 手动 Topic 作为“放入灵龛”的动作；
- 分享卡片上的适度仪式感。

## 裁剪

| v3 功能 | v4 决定 | 原因 |
|---|---|---|
| 充能与徽章 | 删除 | 不要求持续参与 |
| 8 天窗口和提醒 | 删除 | 不制造紧迫感 |
| 8 秒冷静期 | 删除 | 本站不执行写操作 |
| 回魂录与 UGC | 删除 | 不做社区运营 |
| 年度报告 | 暂不做 | 不要求长期积累数据 |
| 私有仓库扫描 | 删除 | 明确隐私边界 |
| 组织版 | 删除 | 不处理组织仓库 |
| 批量归档和改可见性 | 删除 | 不申请仓库写权限 |
| Agent Skill / MCP | 暂不做 | 不属于当前最轻路径 |
| 自动余热提取 | 暂不做 | 需要读取内容、处理授权和导出风险 |
| Secret / CVE 扫描 | 删除 | 超出产品边界，容易产生错误安全感 |
| 用户公开主页 | 不做 | 不让用户维护额外的社交资料 |

### 关于“余热”概念

v4 保留“旧仓库仍可能有价值”的产品表达，但不声称已经自动提取了价值。

最轻的体现是：

- 让用户看到仓库仍有 Star 或 Fork；
- 展示 Fork 来源；
- 提供 GitHub 原仓库链接，方便用户自行查看。

# 十二、GitHub 接入与权限

## 12.1 推荐方式

第一版**不必预设必须使用 GitHub App**。

可以优先评估：

- 使用 GitHub 公开 API 读取符合范围的公开仓库；
- 使用 GitHub 登录验证个人身份；
- 不申请仓库写权限；
- 不申请私有仓库访问权限；
- 不要求组织安装 App。

具体认证方式和权限仍需开发按 GitHub 当前文档核对。

## 12.2 登录说明

登录按钮附近直接说明：

> 登录仅用于确认 GitHub 身份，以及管理你在本站的公开仓库展示。  
> 我们不会要求访问私有仓库或修改仓库的权限。

登录后也只查询和处理用户**个人账户拥有的公开仓库**，不能因为技术上可能访问其他资源就扩大范围。

## 12.3 Topic 发现机制

第一版可以使用公开搜索发现候选仓库，并定期核实已收录仓库。

需要注意：

- GitHub 搜索不保证实时或完整；
- 搜索、分页和 API 都可能受限制；
- 不应把搜索结果当作全量数据库；
- 无法用 GitHub App webhook 直接监听整个 GitHub 上所有仓库的 Topic 变化；
- 手动输入仓库 URL 的收录检查入口，可补充自动发现的遗漏。

# 十三、关键状态与异常

| 状态 | 用户看到什么 | 产品处理 |
|---|---|---|
| 用户名不存在 | `没有找到该 GitHub 用户` | 允许重新输入 |
| 输入的是组织账号 | `本站暂不处理组织仓库` | 不扫描 |
| 个人账户没有公开仓库 | `没有找到可展示的公开仓库` | 提供榜单入口 |
| API 限流 | `暂时无法完成查询，请稍后重试` | 不伪装成空结果 |
| 扫描不完整 | `本次结果可能不完整` | 标明已读取范围和原因 |
| 仓库变为私有或不可访问 | `该仓库当前不可展示` | 从公开列表隐藏 |
| 仓库转入组织 | `本站不处理组织仓库` | 从公开列表隐藏 |
| Topic 已移除 | `仓库已退出灵龛` | 核实后下架 |
| 用户隐藏仓库 | `已在本站隐藏` | 即使 Topic 仍存在，也不重新展示 |
| Fork 上游不可访问 | `无法确认上游状态` | 不推断为删除 |
| 登录用户不是所有者 | `只有当前仓库所有者可以认领` | 拒绝认领 |

# 十四、数据与隐私说明

## 14.1 产品承诺

> 我们只处理个人账户拥有的公开仓库。  
> 不请求私有仓库权限，不扫描组织仓库，不读取仓库代码，不写入或删除 GitHub 仓库。

这里的“不读取代码”意味着第一版只使用必要的公开仓库元数据和允许范围内的比较信息；如果未来要读取文件树或文件内容，需要另行修改产品边界和说明。

## 14.2 可能保存的数据

为支持榜单和认领，可能需要保存：

- 公开仓库标识、名称和 URL；
- 公开仓库的基础统计与更新时间；
- 仓库所属个人账户标识；
- 用户的本站认领关系；
- 用户的隐藏设置；
- 必要的登录会话信息。

不保存私有仓库数据，不保存仓库代码内容。

## 14.3 用户控制

- 可以退出 GitHub 登录；
- 可以查看已认领仓库；
- 可以隐藏仓库；
- 可以删除本站账号及管理记录；
- 可以在 GitHub 撤销应用授权；
- 可以在 GitHub 手动移除 Topic。

删除本站账号和隐藏记录时，需要明确提示：如果仓库仍带有 Topic，未来可能再次被公开发现。用户若希望长期退出，应先移除 Topic，或选择保留最小化隐藏记录。

# 十六、核心验收标准

| 场景 | 验收标准 |
|---|---|
| 未登录查询 | 用户输入个人 GitHub 用户名后，可查看成功读取到的公开仓库；不会因此自动上榜 |
| Topic 收录 | 只有个人公开仓库且带有指定 Topic，才可进入候选池；展示发现延迟说明 |
| 仓库认领 | 只有登录后的当前个人所有者可以认领 |
| 隐藏 | 所有者隐藏后，仓库不再出现在本站公开榜单；后续 Topic 扫描不会覆盖该设置 |
| Topic 移除 | 产品核实 Topic 已移除后下架仓库 |
| 私有化 / 转入组织 | 发现仓库不再符合范围后下架；无法核实时暂时隐藏 |
| 数据不足 | 显示未知或无法获取，不生成确定性判断 |
| 权限 | 不申请私有仓库权限或仓库写权限 |
| 操作边界 | 本站没有归档、删除、同步、修改 Topic 的执行入口 |
| 分享 | 用户主动复制或生成，不自动发布、不自动 @ 他人 |

# 十七、成功指标

轻交互产品不应主要考核用户是否天天回来。

建议关注：

| 目标 | 指标 |
|---|---|
| 用户能快速看到结果 | 用户名查询成功率、查询到结果的耗时 |
| 用户觉得结果有用 | 打开仓库详情或 GitHub 原链接的比例 |
| Topic 路径有效 | 符合条件的 Topic 仓库数、检查收录状态的成功率 |
| 用户能控制展示 | 认领成功率、隐藏操作成功率 |
| 产品值得传播 | 分享链接复制数、分享访问回流 |
| 产品保持可信 | 误收录投诉、下架处理时间、权限相关投诉 |
| 数据质量 | 搜索发现延迟、核实失败率、结果不完整比例 |

**不以打卡天数、日活频率、充能量作为核心指标。**

# 十八、最终版本总结

## 用户只需要记住三句话

1. **想查看自己的公开仓库：输入 GitHub 用户名。**
2. **想让一个仓库进入灵龛：在 GitHub 手动添加 `urn-of-shadows` Topic。**
3. **想管理本站展示：登录 GitHub，认领自己的仓库。**

## 产品只坚持四条边界

1. **只处理个人公开仓库。**
2. **不碰私有仓库和组织仓库。**
3. **默认只读，不修改 GitHub 仓库。**
4. **不要求用户持续参与。**

> **影之灵龛 v4：让一个仓库安静地被看见，也让它随时可以安静地退出。**
