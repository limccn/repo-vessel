# 影之灵龛 Urn of Shadows

## 产品设计方案 v3.0

> **给沉睡的仓库一个归宿，让留下来的代码继续发光。**

**产品定位：**一个面向 GitHub 用户的单页面仓库整理工具。它帮助用户发现沉睡仓库、理解 Fork 与上游的关系、提取仍有价值的内容，并在用户自愿的前提下，将整理过程转化为可分享的故事。

**核心原则：**

> **先理解，再决定；先回收，再处置；默认只读，自愿公开。**

---

# 一、产品重新定义

## 1.1 用户真正需要的不是“清理”

GitHub 用户积累旧仓库后，面临的通常不是单纯的删除问题，而是三个连续的问题：

1. **认不出来**：这个仓库当初为什么创建或 Fork？
2. **不敢处理**：里面是不是还有独有修改、文档或参考价值？
3. **懒得决定**：逐个查看仓库和上游关系的成本太高。

因此，“影之灵龛”不应只是一个仓库墓地，也不应只是一个批量归档工具。

它提供一条完整路径：

```text
发现沉睡仓库
    ↓
理解仓库与上游的现状
    ↓
识别可能值得保留的内容
    ↓
选择保留、归档、唤醒或暂不处理
    ↓
自愿生成故事和分享卡片
```

## 1.2 产品定位调整

| 维度 | v3 定位 |
|---|---|
| 核心价值 | 降低用户整理旧仓库时的信息成本和决策压力 |
| 差异化能力 | Fork 溯源与“余热清单” |
| 基础能力 | 只读扫描、筛选、本站安放、报告导出 |
| 娱乐机制 | 灵龛充能、徽章、故事卡片 |
| 社交传播 | 所有者自愿参与的榜单与年度报告 |
| 操作边界 | 网站默认不修改仓库；删除不由产品执行 |
| 产品形态 | 响应式 Web 单页面，后续扩展 Skill / MCP |

## 1.3 一句话介绍

> **影之灵龛帮你整理 GitHub 上沉睡的仓库：看清 Fork 的来路，找回旧代码的余热，再决定它们的去处。**

# 二、竞品差异化定位

结合上一轮公开资料调研，市场上已经有“仓库墓地”“沉睡项目展示”“Fork 批量清理”和“AI 复活计划”等方向。因此，本产品不应仅靠墓地隐喻或榜单建立差异。

| 产品方向 | 代表案例 | 它们的重点 | 影之灵龛的区别 |
|---|---|---|---|
| 仓库墓地与社区 | VibeCemetery、GitHub Graveyard | 沉睡项目的仪式感、展示和社交 | 社交是可选结果，先解决用户自己的整理问题 |
| AI 复活 | Museum of Dead Dreams、Lazarus | 生成项目故事或继续开发计划 | 不默认“复活”最好，保留和归档也是有效决定 |
| Fork 清理 | GitHub Stale Fork Manager | 找出不活跃 Fork，支持批量处理 | 在操作前重点解释上游、独有修改与不确定性 |
| 仓库治理 | repjan、Stale Repos Action | 仓库筛选、组织盘点、归档候选 | 面向个人的低压力决策与内容回收 |
| 项目发现 | CodeFossils | 浏览和发现旧项目 | 先让所有者整理，再决定哪些内容公开 |

> 上表是基于此前调研形成的定位比较，不应理解为对竞品当前所有功能的穷尽判断。

### 三个差异化支柱

#### 1. Fork 溯源：让用户看清“我和上游有什么关系”

不仅展示“落后多少”，还尽可能回答：

- Fork 来自哪里？
- 上游是否可访问、是否归档？
- 双方是否可以比较？
- 我的 Fork 是否包含上游没有的提交？
- 哪些结论是事实，哪些仍需要人工确认？

#### 2. 余热清单：先发现可保留的东西

帮助用户识别可能值得回看的：

- 文档；
- 脚本；
- 模板；
- 配置示例；
- Fork 中的独有改动。

**第一版只识别候选，不承诺自动判断价值或完成代码迁移。**

#### 3. 低压力决策：不把删除或复活当作唯一目标

让以下结果具有同等地位：

- 保留；
- 入龛；
- 计划唤醒；
- 准备归档；
- 暂时不决定。

# 三、目标用户与使用场景

## 3.1 主要用户

### A. Fork 收藏型开发者

**特征：**经常 Fork 项目学习、修改或收藏，几年后已记不清用途。

**核心问题：**

> “这个 Fork 还有独有改动吗？上游后来怎么样了？”

### B. 独立开发者与实验型开发者

**特征：**创建过许多侧项目、技术实验和半成品。

**核心问题：**

> “哪些项目值得继续？哪些只要留下文档和记忆就够了？”

### C. GitHub 资深用户

**特征：**使用 GitHub 多年，希望整理个人仓库列表。

**核心问题：**

> “我不想删，但希望有一个地方能让我把它们区分开。”

## 3.2 次要用户

- 技术博主：把整理过程转化为故事和分享素材；
- 开源维护者：回看沉睡 Fork 和可能有价值的修改；
- 团队技术负责人：后续盘点组织仓库。

**不建议在第一版面向招聘者设计用户排行。** 仓库沉睡时间不能代表个人能力或工作投入，产品也不应鼓励对开发者作缺乏依据的评价。

# 四、产品世界观与游戏化机制

## 4.1 保留灵感，但不让隐喻妨碍理解

| 产品概念 | 实际含义 | 用户看到的解释 |
|---|---|---|
| **灵龛** | 用户在本站整理仓库的空间 | “你的仓库整理空间” |
| **入龛** | 在本站标记仓库为已安放 | “不会修改 GitHub 仓库” |
| **余烬** | 仓库中可能仍有参考价值的内容或信号 | “值得回看的内容” |
| **充能** | 用户完成整理动作后的游戏化记录 | “仅用于本站展示” |
| **唤醒** | 用户主动决定重新关注仓库 | “计划重新维护” |
| **转生** | 将某些内容迁移到新项目的用户行为 | “需要单独检查权限与许可证” |
| **回魂录** | 用户自愿投稿的整理或复活故事 | “分享你的项目故事” |

### 对外文案原则

- 工具流程使用：`沉睡`、`整理`、`保留`、`归档`；
- 娱乐化区域可以使用：`骨灰盒`、`回魂`、`余烬`；
- 避免使用：`废物项目`、`失败作者`、`垃圾代码`。

## 4.2 充能机制：奖励整理，不奖励荒废

建议不要按“沉睡天数”持续发放充能，否则会让产品看起来鼓励用户放任仓库不维护。

### 建议规则

| 行为 | 充能 | 限制 |
|---|---:|---|
| 首次将一个仓库入龛 | +2 | 每个仓库首次入龛时获得一次 |
| 首次完成有记录的整理决策 | +1 | 每个仓库一次；反复切换状态不重复获得 |
| 自愿提交一篇故事 | 暂不加分 | 避免刷低质量内容 |
| 沉睡时间增加 | 不加分 | 不鼓励为了积分而放任项目 |

**说明：**

- 充能只影响本站的展示与徽章；
- 不代表仓库价值、开发者能力或 GitHub 状态；
- 私有仓库产生的充能默认仅用户自己可见；
- 用户可关闭充能展示。

### 是否采用“8 天窗口”？

**不建议作为默认机制。**

整理旧仓库本身已经有心理负担，如果报告过期、充能衰减或强制倒计时，会制造额外压力。

可保留一个用户主动设置的功能：

> “8 天后提醒我再看一次。”

- 默认关闭；
- 不完成不会扣分；
- 提醒时间可修改；
- 作为待办提醒，而不是惩罚机制。

### “8 秒冷静期”怎么保留？

可用于**未来的高影响批量写操作确认界面**，作为仪式化反馈，而不是唯一的安全措施。真正的保护仍然是：影响预览、权限校验、逐项确认和结果记录。

MVP 没有站内写操作，因此不需要强制倒计时。

# 五、产品信息架构

## 5.1 单页面整体结构

网站以一个响应式页面为主体，使用锚点导航、筛选状态和抽屉承载主要交互。

```text
顶部导航
├── 产品介绍
├── 诊断台
├── 我的灵龛
├── 榜单广场
├── 清理助手
└── 登录 / 设置

首页首屏
├── 产品主张
├── 输入 GitHub 用户名或公开仓库 URL
├── 开始公开预览
└── 查看榜单

诊断台
├── 仓库扫描概览
├── 搜索与筛选
├── 仓库列表
└── 仓库诊断抽屉

我的灵龛
├── 待整理
├── 已安放
├── 计划唤醒
├── 准备归档
└── 忽略

榜单广场
├── 最长沉睡榜
├── 明珠蒙尘榜
├── Fork 时光差榜
└── 其他榜单入口

清理助手
├── 处置清单
├── 命令与官方说明
├── Markdown / JSON 导出
└── Agent Skill 介绍

故事与设置
├── 回魂录
├── 分享卡片
├── 隐私与公开参与
├── 通知设置
└── 数据与授权管理
```

### 关于分享链接

虽然主产品是单页面，但仍可为公开内容提供独立 URL，例如：

- `/r/owner/repo`：经所有者同意公开的仓库档案；
- `/u/username`：用户主动开启的公开灵龛；
- `/story/id`：用户发布的故事。

这些路径可以由同一套前端应用承载，不意味着要为每个功能制作独立页面。

## 5.2 登录与权限分层

| 用户状态 | 可使用能力 |
|---|---|
| 未登录 | 查看首页、公开榜单、公开报告；输入用户名或公开仓库 URL 进行预览 |
| 登录，未授权私有仓库 | 验证身份、保存本站状态、选择自己的公开仓库参与社区 |
| 单独授权私有仓库后 | 在明确范围内扫描授权的私有仓库；默认不公开 |
| 使用本地 Skill | 由用户在自己的环境中提供必要的本地目录和权限 |

**重要边界：**

- 扫描和保存本站状态，不等于修改 GitHub 仓库；
- 在本站“入龛”，不会让仓库从 GitHub 消失；
- 归档是 GitHub 的独立操作，归档后仓库通常仍可查看和搜索；
- 网站不会因为用户登录，就自动将其仓库放进公开榜单。

# 六、核心页面与模块设计

## 6.1 首页：先让用户看到价值

### 首屏文案

**主标题：**

> 你的旧仓库，值得一个好归宿。

**副标题：**

> 找回沉睡的项目，看清 Fork 的来路，留下仍有用的代码与故事。

**输入区：**

```text
输入 GitHub 用户名或公开仓库链接
[ 例如：octocat 或 github.com/owner/repo ] [开始预览]
```

**辅助按钮：**

- `浏览榜单`
- `了解隐私与权限`

**承诺文案：**

> 公开仓库可先预览。默认只读，不会自动删除或修改你的仓库。

### 首屏内容预览

展示三张示意卡片：

1. `沉睡仓库`：多久没有检测到推送；
2. `Fork 来路`：上游关系和可比较状态；
3. `余热清单`：值得回看的文档与脚本候选。

如使用演示数据，必须标注“示例”。

---

## 6.2 诊断台：找到需要处理的仓库

### 扫描入口

用户可以：

1. 输入 GitHub 用户名，预览其公开仓库；
2. 输入单个公开仓库 URL；
3. 登录后扫描自己的公开仓库；
4. 后续版本单独授权私有仓库；
5. 后续版本选择组织及明确的扫描范围。

### 扫描结果概览

| 卡片 | 含义 |
|---|---|
| 已扫描仓库 | 本次成功读取到的仓库数 |
| 长期沉睡 | 超过默认阈值未检测到推送的仓库数 |
| 待查看 Fork | 满足筛选条件、值得用户进一步检查的 Fork |
| 已在本站安放 | 用户在本站标记为“已安放”的仓库 |

点击卡片后，自动筛选列表。

### 列表筛选

**基础筛选：**

- 仓库名称；
- 原创 / Fork；
- 语言；
- 最后推送时间；
- 是否 GitHub 已归档；
- 本站整理状态；
- Star / Fork 数量区间。

**后续增强：**

- 上游状态；
- 是否可比较；
- 是否有领先上游的提交；
- License；
- README 是否存在；
- 是否有未关闭 Issue 或 PR。

### 排序

- 最后推送时间；
- 默认分支最后提交时间，若已获取；
- Star 数；
- Fork 数；
- 仓库创建时间；
- 最近可见 Fork 创建时间，若已获取。

不可获得的数据展示为 `未知`，不能按 `0` 处理。

---

## 6.3 我的灵龛：给仓库一个本站内的去处

### 状态设计

| 状态 | 含义 | 是否修改 GitHub |
|---|---|---|
| 待整理 | 用户还没有决定 | 否 |
| 已安放 | 暂时从本站待整理列表中收起 | 否 |
| 计划唤醒 | 用户想以后重新关注 | 否 |
| 准备归档 | 用户有归档意向，但尚未确认 GitHub 操作 | 否 |
| 忽略 | 不再作为待处理对象提醒 | 否 |
| GitHub 已归档 | 从 GitHub 读取到的实际状态 | 由 GitHub 决定 |

**产品提示：**

> “已安放”只影响影之灵龛中的展示，不会隐藏或修改 GitHub 仓库。

### 灵龛卡片

每个仓库卡片包含：

- 名称与简介；
- 公开 / 私有标记；
- 原创 / Fork；
- 最后推送时间；
- Star / Fork；
- 本站状态；
- GitHub 归档状态；
- `查看诊断`；
- `选择去处`。

### 撤销能力

- 本站状态可随时修改；
- 误入龛可以撤销；
- 站外执行的 GitHub 操作不会因为本站状态变更而自动撤销。

# 七、仓库诊断：事实、判断和建议分开展示

## 7.1 诊断目标

诊断不回答一个绝对的问题：

> “这个仓库值不值得留？”

而是提供用户做决定需要的信息：

> “我们观察到了什么？哪些内容可能需要看一眼？你有哪些选择？”

## 7.2 报告结构

```text
仓库诊断抽屉
├── 1. 基本信息
├── 2. 活动时间线
├── 3. Fork 溯源
├── 4. 余热候选
├── 5. 风险与未知项
├── 6. 可选处理方式
└── 7. 导出与分享
```

### A. 基本信息

- 仓库名称、所有者、描述；
- 创建时间；
- 语言；
- Star / Fork；
- 公开或私有；
- 是否已归档；
- 是否为 Fork；
- 数据更新时间。

### B. 活动时间线

- 最后推送时间；
- 如已获取，默认分支最后提交时间；
- 如已获取，最近 Issue、PR 或 Release 时间；
- 最近可见 Fork 创建时间，若可获取。

**默认沉睡口径：**

> 从仓库最后推送时间到现在的时间。

该口径便于统一筛选，但需注明：

- 推送不等于提交；
- 不一定由仓库所有者本人完成；
- 长期没有推送不等于项目失效；
- 稳定完成的项目可能无需频繁更新。

### C. 诊断结果示例

```text
这个仓库已沉睡约 892 天

已知：
- 最后推送：2024-05-20
- 仓库类型：Fork
- GitHub 状态：未归档
- 上游状态：可访问，最近仍有推送

尚未确认：
- 你的独有修改是否已被上游吸收
- 仓库中的文档是否仍适合复用

可选下一步：
[查看 Fork 差异] [保留参考] [计划唤醒] [准备归档]
```

## 7.3 暂不使用“总分”作为核心结论

你提出了休眠指数、健康评分、可回收性评分和雷达图。这些视觉形式有吸引力，但第一版容易产生两个问题：

1. 用户不知道分数如何计算；
2. 数据不足时，分数会制造虚假的确定性。

**v3 建议：**

- MVP 使用可解释的状态标签和事实清单；
- 每项结论标明依据与数据时间；
- 后续若推出评分，必须公开规则、缺失项和适用范围；
- 不用“沉没成本人时”替用户估算投入。

Commit 数、代码行数和仓库年龄不能可靠换算为工作小时数。可以展示“可观察的项目规模”，但不展示“你浪费了 200 小时”这类结论。

# 八、Fork 溯源：核心差异化模块

## 8.1 目标

帮助用户回答：

> “这个 Fork 与上游之间发生了什么，我是否还有独有内容需要保留？”

## 8.2 溯源视图

```text
你的 Fork
alice/project
最后推送：892 天前
        ↓
直接来源
team/project
最后推送：45 天前
        ↓
根仓库
original/project
状态：可访问 / 已归档 / 未知
```

### 展示原则

- 仅展示 GitHub 返回且用户有权限访问的关系；
- 如果只能获取直接来源，不强行补全根仓库；
- 仓库重命名或转移后，以实际可解析的仓库信息为准；
- 上游不可访问时，展示“不可访问或不存在”，不直接断定“已删除”。

## 8.3 差异面板

当双方分支可访问、存在可比较关系且 API 能返回结果时，展示：

- 比较的基准分支和目标分支；
- Fork 相对上游领先的提交数；
- Fork 相对上游落后的提交数；
- 最后比较时间；
- 数据缺失或比较失败的原因。

**特别说明：**

- 比较结果依赖选择的分支和提交历史；
- 领先 / 落后数量不直接代表代码质量或价值；
- 没有领先提交，不等于用户没有值得保留的其他信息，例如 Issue、Wiki 或发布记录；
- “上游已经修复同一个问题”通常不能仅凭提交数可靠判断。

## 8.4 诊断状态与建议

| 状态 | 可以确认的事实 | 建议 |
|---|---|---|
| 上游活跃，Fork 较久未更新 | 上游有近期活动，Fork 沉睡 | 查看变化，决定继续 Fork、同步或直接参考上游 |
| Fork 存在领先提交 | 当前比较中发现上游没有的提交 | 先检查独有改动，不建议直接丢弃 |
| 未发现领先提交 | 在当前比较范围内未发现领先提交 | 可检查是否还有 Issue、文档、其他分支等需要保留 |
| 上游已归档 | GitHub 显示上游已归档 | 可作为历史参考，或评估是否继续维护 |
| 上游不可访问 | 当前无法读取上游 | 保留现状并手动核实；不推断上游已删除 |
| 无法比较 | 分支、权限或历史不满足比较条件 | 告知原因，建议在本地进一步检查 |
| 不是 Fork | 仓库没有 Fork 关系 | 进入普通仓库诊断 |

### “我的改动已被上游合并”怎么判断？

只有在存在足够证据时才展示，例如关联到可确认的已合并 PR。即使存在已合并 PR，也不代表 Fork 的**全部**独有修改都已经被吸收。

因此，建议文案是：

> “发现一个可能相关的已合并 PR，请检查你的其他改动。”

而不是：

> “你的所有修改已合并，可以删除 Fork。”

### 冲突文件

“冲突文件列表”需要明确比较的具体分支和合并方式，通常还需要执行试合并或其他实际计算。

- MVP：不承诺提供；
- 后续：可由本地 Skill 在用户授权的仓库副本中执行检查；
- 结果只说明在指定条件下是否产生冲突，不保证未来合并一定相同。

# 九、余热提取：从“发现候选”开始

## 9.1 功能定位

“余热提取”是 v3 的第二个核心差异化，但应分成两个层次：

1. **网站识别候选**：提示哪些内容可能值得回看；
2. **用户本地提取**：在明确授权下，通过工具或 Agent 完成导出。

不应在没有读取内容的情况下宣称已经理解某份文档或识别出全部独有价值。

## 9.2 余热清单

在用户允许读取必要信息的前提下，候选类别可以包括：

| 类别 | 示例 | 产品表达 |
|---|---|---|
| 文档 | `README`、`docs/` | “发现可能值得回看的文档” |
| 脚本 | `scripts/`、构建脚本 | “发现可检查的脚本文件” |
| 模板 | 配置模板、示例项目 | “发现可能可复用的模板” |
| Fork 改动 | 领先上游的提交或文件 | “发现需要人工检查的差异” |
| 故事线索 | 用户自己填写的项目说明 | “记录你为什么想保留它” |

**不是所有候选都一定有价值，也不是所有有价值的内容都能自动发现。**

## 9.3 读取与隐私边界

扫描能力分层：

| 能力 | 所需数据 | 用户提示 |
|---|---|---|
| 基础诊断 | 仓库元数据 | 默认只读，不读取代码内容 |
| 目录候选识别 | 文件树或路径信息 | 可能暴露项目结构，需说明 |
| 内容分析 | README、脚本等文件内容 | 需单独明确同意，并说明处理位置 |
| 本地导出 | 本地仓库与用户指定目标目录 | 由本地工具执行，不默认上传 |

**MVP 建议：**网站只做元数据诊断。余热提取先提供用户检查清单与本地工具说明，不承诺服务端读取、分析或保存代码。

## 9.4 复用前提醒

提取不等于可以任意重新分发。产品需要提醒用户检查：

- 仓库 License 是否允许预期用途；
- 是否包含第三方代码或素材；
- 文档和配置中是否有敏感信息；
- 迁移到新仓库是否会意外公开私人内容。

# 十、处置向导与清理助手

## 10.1 向导的目的

把用户从“这个仓库该怎么办？”引导到一个可理解、可撤销或可审查的决定。

### 建议的四步流程

```text
第 1 步：确认仓库现状
        ↓
第 2 步：检查是否有内容需要保留
        ↓
第 3 步：选择去处
        ↓
第 4 步：查看影响并记录结果
```

### 选项

| 选项 | 实际动作 |
|---|---|
| 保留参考 | 在本站记录保留原因 |
| 入龛安放 | 从本站待整理列表收起 |
| 计划唤醒 | 加入待关注列表 |
| 准备归档 | 展示 GitHub 归档影响、入口和命令说明 |
| 提取余热 | 查看本地检查与导出指引 |
| 暂不决定 | 保持待处理，不扣分、不提醒，除非用户主动设置 |

## 10.2 命令与官方说明

网站可以展示可复制的命令，但必须先显示目标仓库和操作影响。

例如：

```bash
gh repo view OWNER/REPO
```

准备归档时，可展示：

```bash
gh repo archive OWNER/REPO
```

旁边明确提示：

- 需要本地安装并登录 GitHub CLI；
- 当前账户需要相应权限；
- 归档会改变 GitHub 仓库状态；
- 归档不等于删除，通常可以在 GitHub 上取消归档；
- 复制命令不代表已经执行；
- 产品不应假装可以验证用户在终端里执行了什么。

对于 `git bundle`、`git filter-repo`、`rsync` 等涉及本地路径、历史重写或覆盖风险的命令，MVP 不生成通用的一键命令；先提供说明与检查步骤，后续由本地工具根据实际环境生成并让用户审阅。

## 10.3 “待遗忘区”的正确含义

建议保留这个概念，但重新定义：

> **待遗忘区 = 本站内等待用户复查的整理清单，而不是 GitHub 仓库的回收站。**

- 用户可以将“准备归档”的仓库放入待复查列表；
- 用户可以设置 30 天后提醒；
- 这 30 天不会自动归档或删除仓库；
- 本站不能保证恢复已在 GitHub 或本地执行的所有操作；
- GitHub 已归档的仓库是否可取消归档，应由用户在 GitHub 中确认和执行。

# 十一、Agent Skill / MCP 设计

## 11.1 定位

> 让用户自己的 Agent 读取诊断结果，生成整理计划，并在明确授权后辅助本地检查。

Skill 是使用说明与流程约束；MCP 是可供兼容客户端调用的工具接口。两者可分别推出，不必在 MVP 同时建设。

## 11.2 建议能力

| 能力 | 作用 | 默认权限 |
|---|---|---|
| `urn.diagnose` | 汇总仓库现状 | 只读 |
| `urn.trace_fork` | 检查来源、上游与比较状态 | 只读 |
| `urn.suggest_disposal` | 生成带依据的处理计划 | 只读 |
| `urn.export_assets` | 按用户指定路径导出选中内容 | 涉及本地写入，需明确确认 |

### 处置计划格式

```text
仓库：
已知事实：
未知事项：
可能值得保留的内容：
候选处理方式：
每种方式的影响：
需要用户确认的事项：
已执行 / 未执行：
```

## 11.3 安全约束

- 默认只读；
- 仓库文件、Issue 和 README 中的文字视为待分析内容，不视为给 Agent 的高优先级指令；
- 不读取与任务无关的文件、凭据或密钥；
- 私有仓库内容不发送给未经用户同意的外部服务；
- 导出前展示源路径、目标路径和覆盖风险；
- 写操作逐项确认，并记录结果；
- 不提供自动删除仓库；
- 日志需说明“记录了什么”，不能承诺所有操作均可回滚。

### 与网站权限的关系

即使未来 Agent 支持归档、修改 Topic 或写入 Badge：

- 这些仍是 GitHub 写操作；
- 需要用户在自己的环境中拥有相应权限；
- 不能通过网站的只读授权完成；
- 产品需明确区分“网站未写入”和“用户授权 Agent 写入”。

# 十二、榜单与社区：默认不公开，参与靠自愿

## 12.1 公开规则

**默认不公开，主动加入。**

1. 用户登录并验证自己的 GitHub 身份；
2. 选择自己有权公开参与的公开仓库；
3. 预览展示字段；
4. 确认加入社区；
5. 可以随时撤回。

### 可见性设置

| 选项 | 说明 |
|---|---|
| 完全隐藏 | 默认状态，不进入公开榜单 |
| 公开仓库名与所有者 | 标准公开参与 |
| 匿名故事 | 不展示 GitHub 用户名与仓库链接，但不能保证内容完全无法被识别 |

**匿名不能同时展示可识别的仓库链接。** 如果用户希望公开链接，就应清楚告知仓库所有者信息通常可被推知。

### 私有仓库

- 不进入公共榜单；
- 不生成包含仓库名、URL、代码内容的公开卡片；
- 如未来允许用户分享聚合统计，也应单独预览和确认，并提醒聚合数据仍可能泄露信息。

## 12.2 榜单设计

### MVP 三个榜单

#### A. 最长沉睡榜

- **入榜对象：**所有者主动参与的公开仓库；
- **默认排序：**最后推送时间从早到晚；
- **卡片文案：**`已沉睡约 1,024 天`；
- **说明：**只代表仓库推送时间，不代表开发者不活跃。

#### B. 明珠蒙尘榜

- **入榜条件：**超过设定时间无推送，且有一定 Star 数；
- **默认排序：**Star 数；
- **筛选：**沉睡时间、语言、Fork / 原创；
- **文案：**`虽然安静，仍有人记得它。`

第一版不建议使用“Star 数乘沉睡天数”作为唯一排名，因为该公式会让排序依据变得不直观。可以提供两项独立排序。

#### C. Fork 时光差榜

- **入榜条件：**用户主动公开的 Fork，且上游与选定分支可以比较；
- **默认排序：**相对上游落后的提交数；
- **展示：**比较分支、更新时间及数据限制；
- **文案：**`上游继续前进，而这个 Fork 停在了另一个时间点。`

“落后更多”只是趣味指标，不代表用户应该同步。

### 后续榜单

| 榜单 | 玩法 | 注意事项 |
|---|---|---|
| 仍在传承榜 | 长期沉睡但最近仍被 Fork | 最近 Fork 时间不可获取时显示未知 |
| 上游已归档榜 | 展示上游已归档的 Fork | 不把不可访问直接称为“上游已死” |
| 孤本收藏榜 | 用户主动分享的小众项目 | 不以代码行数判断价值 |
| 唤醒故事榜 | 用户主动提交重新维护的故事 | 不单靠一次提交判定“复活成功” |
| 灵龛充能榜 | 用户主动公开自己的本站充能 | 默认关闭，防刷规则单独设计 |
| 回响贡献榜 | 分享经验、帮助他人的用户 | 应防止低质量刷互动 |

### 不建议直接上线“沉没成本榜”

Commit 数、年龄和代码行数无法可靠估算投入工时。可以改为：

> **项目足迹榜：展示用户自愿分享的仓库历史。**

不自动生成“浪费了多少小时”的结论。

## 12.3 筛选与时间切片

### 通用筛选

- 语言；
- 原创 / Fork；
- 沉睡时长；
- Star / Fork 数量；
- 是否已归档；
- 是否有可用上游信息。

### 排序

- 最后推送时间；
- 默认分支最后提交时间；
- Star；
- Fork；
- 仓库年龄；
- 最近可见 Fork 创建时间。

对于未采集或不适合全量计算的字段，例如代码行数、CI、测试、贡献者数，**不作为 MVP 所有榜单的通用排序条件**。

### 时间切片

需明确时间切片针对什么事件：

- `7 / 30 / 90 / 365 天新入榜`：按用户确认公开的时间；
- `最近唤醒`：按用户提交唤醒故事的时间；
- `最近更新`：按仓库推送时间。

不能把不同事件混在一个“最近 30 天”筛选里。

## 12.4 社区互动

MVP 可先保留一种轻互动：

- `🕯️ 点亮余烬`

后续再考虑：

- 共鸣；
- 故事评论；
- 诊断心得；
- 用户投稿。

### 分享边界

不提供默认点名或批量“召唤”他人的功能。

用户可以分享**自己选择公开的仓库**，但产品不应自动生成用于嘲讽或骚扰他人的内容。对于其他人的公开仓库，是否允许分享及如何下架，需要另行制定规则。

### 徽章

| 徽章 | 获得方式 |
|---|---|
| 灵龛初成 | 首次入龛 |
| 守龛人 | 完成一定数量的整理决策 |
| 回魂师 | 自愿记录多个唤醒故事 |
| 余烬收藏家 | 记录值得保留的项目内容 |
| 灵龛满载 | 达到某个充能里程碑 |

徽章显示在本站。若要添加到 GitHub README，必须由用户自行复制或明确授权写入。

# 十三、Topic 机制：作为参与信号，而不是唯一采集路径

## 13.1 推荐定位

`urn-of-shadows` Topic 可以成为产品的社区入口和用户自愿标记，但不应作为 MVP 的唯一数据来源。

### 可行流程

```text
用户手动给公开仓库添加 Topic
        ↓
用户登录本站并提交仓库 URL
        ↓
本站验证仓库所有权、公开状态及 Topic
        ↓
预览并确认公开展示
        ↓
加入社区候选池
```

### 为什么不完全依赖 Topic 自动采集？

- 添加 Topic 是 GitHub 写操作，不能由只读授权自动完成；
- GitHub 搜索结果可能受索引延迟、限流和查询限制影响；
- GitHub App 的 webhook 并不是对全 GitHub 仓库 Topic 变化的全局订阅；
- webhook 事件范围取决于 App 的安装、权限和具体事件能力，需在开发时按官方文档验证；
- 仓库有某个 Topic，并不必然清楚地等于同意本站长期公开展示。

### v3 推荐

- **主路径：**登录后主动选择公开仓库并确认；
- **辅助路径：**Topic + 用户主动提交 URL；
- **后续能力：**在产品明确安装范围后，评估 GitHub App 的 webhook 和增量更新。

### 退出方式

用户可在本站撤回公开参与。

如果通过 Topic 加入，本站还应提示：

> “如不希望后续通过 Topic 被再次发现，请同时在 GitHub 中移除该 Topic。”

# 十四、分享、年度报告与内容传播

## 14.1 分享卡片

### 卡片类型

1. **仓库故事卡**  
   展示一个用户主动公开的仓库和一句寄语。

2. **整理成就卡**  
   展示用户选择公开的整理数量或徽章。

3. **Fork 时光卡**  
   展示 Fork 与上游的公开比较结果，并注明比较时间。

4. **唤醒故事卡**  
   分享用户重新关注某个项目的原因。

### 示例

```text
它已经安静了 892 天。

但这个仓库让我第一次学会了
如何为开源项目提交 Pull Request。

— alice / project
```

### 分享控制

分享前必须预览：

- 仓库名和所有者；
- 仓库链接；
- 时间与统计字段；
- 用户填写的文字；
- 品牌标识。

用户可以取消分享，也可以撤回本站公开页面。已经被第三方截图、缓存或转发的内容，产品无法保证全部收回，需在分享前提示。

## 14.2 年度报告

可以作为后续的重要传播节点，但不建议在 MVP 承诺完整的“历史年度报告”。

建议内容：

- 今年在本站整理了多少仓库；
- 自己选择公开的代表项目；
- 最长沉睡项目；
- 一段用户自己填写的项目故事；
- 今年主动记录的唤醒事件。

**数据限制：**

- 产品只能统计实际采集或用户记录的数据；
- 缺失历史数据时不编造；
- 不估算“浪费工时”；
- 不把私有仓库名称自动放入报告；
- 用户需逐项确认分享内容。

# 十五、视觉设计方向

## 15.1 风格定位

**关键词：深色、安静、温暖、微游戏化。**

不同于偏“死亡墓地”的表达，视觉重点放在：

> **一只收藏余烬的容器，而不是一个埋葬失败的墓园。**

## 15.2 色彩与组件

| 元素 | 建议 |
|---|---|
| 背景 | 深灰蓝、近黑色 |
| 主强调色 | 柔和青绿色幽光 |
| 次强调色 | 暗金色 |
| 文本 | 柔和米白，保证对比度 |
| 警示 | 琥珀色 |
| 高风险操作 | 明确的红色提示 |
| 主视觉 | 自绘抽象灵龛与充能刻度 |
| 仓库卡片 | 信息密度适中，状态清晰 |
| 诊断抽屉 | 工具感优先，减少装饰 |
| 榜单区域 | 可适度加入游戏 UI 和趣味动效 |

## 15.3 状态设计

至少覆盖：

- 未输入；
- 扫描中；
- 扫描完成；
- 无沉睡仓库；
- 仓库为空；
- 上游不可访问；
- 无法比较；
- API 限流；
- 登录取消；
- 权限不足；
- 私有仓库未授权；
- 公开分享确认；
- 公开参与已撤回；
- 网络错误与重试。

# 十六、权限、技术与数据边界

<details>
<summary><strong>供产品经理、技术负责人讨论的实现约束</strong></summary>

## 16.1 授权方案不应直接照搬宽权限 Scope

草案中提出的 `public_repo` 和 `repo` 并不适合直接描述为“只读仓库权限”：经典 OAuth Scope 中，它们可能带来比只读更广的仓库访问能力。

建议：

1. **公开预览：**优先使用公开数据访问，不要求用户一开始授予仓库写权限；
2. **身份验证：**只申请登录所需的最小信息；
3. **私有仓库：**如后续需要，评估使用 GitHub App 等更细粒度的权限机制，明确选择仓库和读取范围；
4. **写操作：**与只读扫描分离，按具体动作另行授权；
5. 上线前由开发逐项核对 GitHub 当前权限和 API 文档。

不要在权限页面写“只读”，却实际申请具有写能力的宽泛 Scope。

## 16.2 “只读元数据”不等于可以完成所有诊断

以下能力通常需要更多数据，不能与“只读取元数据、不读代码”混为一谈：

- README 完整度；
- CI 和测试检查；
- 文件级差异；
- 依赖分析；
- Secret 扫描；
- 独有内容提取；
- License 内容分析。

这些应拆为独立能力，并分别说明读取范围、处理位置和保存方式。

## 16.3 本地未推送内容无法从 GitHub 扫描

网站无法仅通过 GitHub API 知道用户电脑上是否存在：

- 未推送分支；
- 未提交修改；
- 本地未跟踪文件。

这些只能在用户本地授权工具访问对应目录后检查，且只覆盖该设备和被检查的路径。

同样，Issue、PR 和 Wiki 的导出也不等于普通 `git bundle`：它们需要分别检查和处理。

## 16.4 数据保存建议

MVP 只保存完成产品功能所需的信息，例如：

- GitHub 用户标识；
- 用户选择的本站状态；
- 经同意公开的仓库和展示字段；
- 充能事件；
- 用户主动填写的故事；
- 必要的缓存和数据更新时间。

默认不保存仓库代码内容。是否保存私有仓库元数据、保存多久、如何删除，需要在支持私有仓库之前单独设计并公开说明。

## 16.5 数据来源限制

- GitHub API 与搜索有速率、权限、分页和索引限制；
- 缓存和增量扫描可以降低压力，但不能保证实时；
- GH Archive 等公开事件数据不应被视为私有数据来源，也不能保证覆盖所有历史状态；
- 每个报告和榜单显示数据更新时间；
- 刷新失败时保留明确的过期提示，不把旧数据伪装成实时结果。

## 16.6 安全诊断边界

Secret、CVE、License 兼容性和替代品推荐都属于高复杂度能力。

第一版不承诺：

- 完整识别所有泄露的 Secret；
- 识别所有漏洞；
- 给出法律意义上的 License 兼容性结论；
- 自动判断某项目“已被替代”。

后续如提供，必须说明覆盖范围、误报漏报和数据来源，并优先考虑用户本地执行。

# 十七、关键用户流程

## 流程一：未登录预览

```text
进入首页
→ 输入 GitHub 用户名
→ 查看公开仓库扫描结果
→ 按沉睡时间或 Fork 筛选
→ 打开单个仓库诊断
→ 如需保存整理状态，再登录
```

**预期结果：**用户不必先授权，就能判断产品是否有用。

---

## 流程二：整理自己的 Fork

```text
登录
→ 扫描自己的公开仓库
→ 筛选 Fork
→ 查看上游状态和比较结果
→ 查看未知事项
→ 选择保留、入龛、计划唤醒或准备归档
→ 保存本站决定
```

**预期结果：**用户完成一个有依据的决定，而不是被迫删除。

---

## 流程三：提取余热

```text
打开仓库诊断
→ 查看建议检查的内容类别
→ 用户确认是否需要进一步读取文件或在本地检查
→ 查看候选内容
→ 检查 License、敏感信息和目标路径
→ 用户自行导出，或使用后续本地 Skill
→ 记录已完成 / 未完成
```

**预期结果：**先保护内容，再考虑仓库去处。

---

## 流程四：自愿加入社区

```text
选择自己的公开仓库
→ 查看将公开的字段
→ 选择榜单或生成故事卡
→ 确认公开
→ 获取分享链接
→ 随时撤回本站公开展示
```

**预期结果：**传播由仓库所有者发起，不自动曝光。

# 十八、版本规划

## MVP：验证“整理决策”是否成立

### 必做

1. 首页与公开仓库预览；
2. GitHub 登录；
3. 扫描用户自己的公开仓库；
4. 沉睡时间与 Fork 筛选；
5. 单仓库基础诊断；
6. Fork 来源和上游可访问 / 归档状态；
7. 能可靠获取时展示基础分支比较；
8. 本站整理状态；
9. Markdown / JSON 整理清单导出；
10. 所有者主动选择公开仓库；
11. 三个轻量榜单：最长沉睡、明珠蒙尘、Fork 时光差；
12. 一种分享卡片；
13. 隐私、退出展示和数据删除入口。

### 暂不做

- 私有仓库扫描；
- 网站内批量归档或修改可见性；
- 自动删除；
- 自动判断上游已修复全部问题；
- 服务端 Secret 扫描；
- 自动提取和合并代码；
- 组织版；
- 完整年度报告；
- 全量 Topic 自动采集。

> 草案中的“4–6 周”可作为小团队探索目标，但是否能按期完成，取决于人员、GitHub 接入方案、榜单数据量和设计复杂度。建议先做技术验证，再确定排期。

## V1：增强 Fork 与余热体验

- 目录级余热候选识别，单独说明权限；

## V2：Agent 与内容社区

- 可选 MCP 接口；

# 十九、指标体系

## 19.1 北极星指标

建议将“周活跃处置数”调整为：

> **每周完成至少一次有依据整理决定的用户数。**

原因：同一用户批量标记大量仓库可能抬高“处置数”，但不一定代表真正获得价值。

### “完成整理决定”的定义

用户查看了仓库信息后，主动选择以下任一项：

- 保留参考；
- 入龛安放；
- 计划唤醒；
- 准备归档；
- 忽略。

这些是**本站记录的决定**，不应默认计为 GitHub 操作已执行。

## 19.2 配套指标

| 类别 | 指标 |
|---|---|
| 获客 | 用户名预览启动数、分享链接访问数 |
| 激活 | 扫描成功率、首次查看诊断的用户比例 |
| 核心价值 | 完成首次整理决定的用户比例 |
| Fork 价值 | 打开 Fork 溯源面板的比例、查看差异后的决策比例 |
| 余热价值 | 打开余热清单、导出整理报告的用户数 |
| 留存 | 7 日 / 30 日回访及再次整理比例 |
| 传播 | 分享卡生成数、主动分享数、有效回流 |
| 信任 | 授权取消率、公开参与撤回率、误展示投诉 |
| 数据质量 | 上游解析成功率、比较失败率、数据过期比例 |

### 防止虚荣指标

不把以下行为单独视为成功：

- 榜单停留时间长；
- 生成大量充能；
- 扫描仓库数量多；
- 用户反复切换本站状态；
- 用户复制了命令但未确认是否使用。

# 二十、需要 PM 与团队确认的关键决策

1. **主线是否确定为“个人整理优先，社区传播其次”？**
2. **MVP 是否只支持公开仓库，私有仓库后置？**
3. **Fork 比较在 MVP 中做到什么程度？** 是只展示来源和上游状态，还是包含可比较分支的领先 / 落后数？
4. **余热提取第一版是否只做检查清单与导出指引？**
5. **公开榜单是否坚持默认隐藏、主动加入？**
6. **Topic 是辅助参与方式，还是未来要建设更复杂的发现机制？**
7. **网站是否长期保持不写入，还是未来单独申请写权限？**
8. **充能是否只奖励首次整理行为，不按沉睡时间持续增加？**
9. **年度报告是否作为后续传播事件，而不是 MVP 交付目标？**
10. **组织版只预留数据模型，还是会进入近期路线图？**
